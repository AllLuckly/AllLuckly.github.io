Use an authorized source to record web sign-in, return to the source and a known search as separate steps.

Check the update and applicability

Apple’s public Manyue 2.0.7 notes mention a fix for possible incorrect return after source web login. This exercise applies only to a source you are authorized to use that actually presents web login in Manyue. Not every source requires an account or supports web authorization. Without one, mark the exercise unperformed; do not create an account or add an unknown script just to test.

Prepare an identifiable starting point

Confirm the installed version and choose your own trusted source. Note its public name and current location, such as source details or search. Choose a known keyword for content you can lawfully access; do not record accounts, tokens, verification codes or private addresses. Note any existing reading or download activity so it is not confused with login. Do not clear existing data as preparation.

Separate three starting states

Make columns for the Manyue page, source web state and search result. Before signing in, record the selected source and visible prompt. If the page already appears signed in, follow that source’s rules to decide whether a new login is necessary; do not force a sign-out. Mark the starting state signed in, signed out or unknown instead of assuming it. If searching before login is allowed and the user wishes, search the prepared keyword in the same source and record the result and time. Otherwise mark the search baseline unperformed.

Open the available web entry

Open the sign-in or web entry actually shown by the selected source. If no entry is available or the source reports it unsupported, stop and record that result. Do not invent a button or substitute another server’s login page. Confirm the displayed domain and source are trusted before continuing. Do not accept unfamiliar downloads, requests for personal details or permissions just to finish the exercise.

Let the user complete normal sign-in

The user signs in with an authorized account according to the source page, entering credentials and verification themselves. Record only success shown, failure shown or incomplete; do not retain credentials or sensitive screenshots. If additional verification is declined, stop and mark incomplete. Page changes or service maintenance may affect the result and are not direct proof of an app navigation issue.

Observe the return destination

After sign-in, use the close or return action actually provided and record both the action and destination. Compare the source name with the baseline to see whether the expected source or related page is visible. If a different location appears, record the visible title, action and conditions rather than clicking blindly until the shelf appears. Closing an incomplete login is not a post-login return test.

Check identity and login separately

After returning, confirm the selected source is the same one and look for an identifiable account state if the interface offers one; otherwise record unknown. A correct return does not guarantee sign-in succeeded, and a success message does not establish permission for every comic. A shared nickname, neighboring source or cached content is insufficient proof of the same account.

Repeat the same search

Search the recorded keyword in the same source and observe a list, empty result or explicit error. Only compare with a pre-login search that was actually performed, keeping network and keyword constant and recording the time; otherwise record this search alone, without treating an empty baseline as a comparison. If content needs additional permission, follow the source’s rules rather than bypassing them. On failure, check the source service and network, then separate sign-in, return and search stages.

Use an optional cancellation control

Only when the user already has a suitable test account and wants to participate, record a separate cancellation path: open the page, cancel and observe where it returns. Do not sign out of the sole account or change security settings for this control. Keep cancellation and successful login in separate rows, and mark an unperformed row as such.

Troubleshoot and retain the result

If web login succeeds but return is unexpected, record app version, public source name, starting page, close method, destination and non-sensitive error text. Hide accounts, credentials, tokens and private addresses. If search still fails, verify login and source authorization before considering more disruptive changes; do not reinstall or clear all history first. Keep the old result and add a new row after retry. The author has not signed in to a private account or tested a device.

Compare networks without mixing conditions

If the device normally uses Wi-Fi and cellular, and the user agrees and understands data charges, record each connection separately using the same source and keyword. Observe the current network first; do not disable protection or change the router. Login state may differ, so label it for each row. A web success before switching does not establish app login afterward. Mark the comparison unperformed when no suitable network exists.

Separate return from background restoration

If the user switches to another app while login is open and later returns, record that as an extra condition. Background restoration is not identical to normally closing the web page. Complete the no-switch baseline first, then observe restoration separately only if needed. If the system requests verification, the user decides whether to continue; do not record verification codes. Separate paths prevent confusing restoration behavior with a normal post-login return.
