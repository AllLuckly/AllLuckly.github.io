MVC is a software architectural pattern that divides a system into three basic parts: Model, View, and Controller. It aims to support flexible program design, simplify later modifications and extensions, and make parts of the program reusable.

Editor: Bison
Source: Sindri’s Notes

The title is awkward, but after much thought I could not find a better one. This article owes part of its inspiration to An analysis of the current state of iOS apps, and the title comes from its phrase “distribute code responsibilities evenly among different functional classes.” Readers of my articles may know that I mainly use MVC for most development. My projects have not been particularly large, and sensible division of responsibilities has kept them in good shape, so I have not developed projects with other architectures. If you are in a similar position, you should still study other patterns even if you do not use them.


Briefly, I have wanted to write this article for a long time. The idea arose during conversations while interviewing iOS developers. The dialogue below is a composite I put together, not a portrayal of a particular person:

Q: Your project uses MVVM. Why did you choose that structure?

A: During development, controller code kept growing beyond a thousand lines. We felt the controllers had too many responsibilities, so we used ViewModels to separate them.

Q: Can you describe your controllers' responsibilities, or show some source code?

The interviewee opens the source code on a computer.

Ultimately, I do not think the interviewee needs MVVM to improve their architecture. Opinions may differ here, but their unreasonable division of responsibilities caused View and Model layer contains almost no business logic, leaving the controller unbalanced and bloated. In this situation, even using ViewModel separates the controller's code, but at most it merely 将垃圾挪到另一个地方罢了. In Thoughts on MVC architecture I discussed my understanding of MVC three modules' responsibilities. When you want to change MVC into MVX with another structure, first consider whether your code's responsibilities are balanced.

Developer Xiaoming's project

Before we begin, I strongly recommend 《重构-改善既有代码的设计》 (Refactoring: Improving the Design of Existing Code) again. A good book or article should offer a different impression each time you return to it.

Do not rush to laugh at code like this; we have written similar code ourselves. It is the most obvious kind of duplication: lengthy, meaningless, and taking up space. Repeated code is often scattered across classes and gradually makes the project unwieldy. Before discussing whether the architecture needs improvement, ask whether you first need to remove this clutter.

For example, Xiaoming builds a business-facing app where merchants can add promotions with start and end dates:

While optimizing after development, Xiaoming noticed this repeated code in several modules. He wrote an NSDate extension to simplify it and added a safety check:

@implementation NSDate (convenience)

- (BOOL)betweenFront: (NSDate *)front andBehind: (NSDate *)behind {
    if (!front || !behind) { return NO; }
    return ([self timeIntervalSinceDate: front] > 0 && [self timeIntervalSinceDate: behind] < 0);
}

@end

Some time later, the product manager told Xiaoming that merchants needed several different promotions rather than only one. Xiaoming decided to remove the singleton nature of Promotion and introduce a manager singleton:

@interface PromotionManager: NSObject

@property (readonly, nonatomic) NSArray<Promotion *> * promotions

+ (instancetype)sharedManager;
- (void)requestPromotionsWithComplete: (void(^)(PromotionManager * manager))complete;

@end

//  module A
- (void)viewDidLoad {
    PromotionManager * manager = [PromotionManager sharedManager];
    if (manager.promotions) {
        [manager requestPromotionsWithComplete: ^(PromotionManager * manager) {
            _promotions = manager.promotions;
            [self calculateOrder];
        }
    } else {
        _promotions = manager.promotions;
        [self calculateOrder];
    }
}

- (void)calculateOrder {
    CGFloat orderAmount = _order.amount;
    for (Promotion * promotion in _promotions) {
        if ([[NSDate date] betweenFront: promotion.start andBehind: promotion.end]) {
            orderAmount *= promotion.discount;
        }
    }
}

Requirements grew over time. One day, the product manager wanted merchants to enable and disable promotions freely, so Promotion gained an isActived property. Other modules now checked both time and activation. Later, synchronize determined whether a promotion could combine with others. Most recently, discounts expanded to fixed reductions and spending-threshold offers, producing the following code:

By now, retrieving promotion information cost each module a long block of highly repetitive code. A colleague suggested changing the architecture and moving it out of controllers into a ViewModel. But the purpose of ViewModel here was essentially the same as Xiaoming's earlier NSDate extension. The View and Model were doing almost nothing, while nearly all logic kept bloating the controller. After carefully reviewing everything, Xiaoming concluded that confused responsibilities were the main problem: the code could not be cleanly separated into VC modules. The solution should begin by dividing logical responsibilities.

First, Xiaoming noticed that Promotion only stored promotion information and performed no logic. The controller's business logic for checking validity and calculating discounts could belong to Promotion:

@interface Promotion: NSObject

- (BOOL)isEffective;
- (BOOL)isWorking;
- (CGFloat)discountAmount: (CGFloat)amount;

@end

@implementation Promotion

- (BOOL)isEffective {
    return [[NSDate date] betweenFront: _start andBehind: _end];
}

- (BOOL)isWorking {
    return ( [self isEffective] && _isActived );
}

- (CGFloat)discountAmount: (CGFloat)amount {
    if ([self isWorking]) {
        if (_promotionType == PromotionTypeDiscount) {
            return [self calculateDiscount: amount];
        } else {
            if (amount < _discountCondition) { return amount; }
            return [self calculateDiscount: amount];
        }
    }
    return amount;
}

#pragma mark - Private
- (CGFloat)calculateDiscount: (CGFloat)amount {
    if (_discountType == DiscountTypeCoupon) {
        return amount - _discount;
    } else {
        return amount * _discount;
    }
}

@end

Finally, other modules contained extensive logic for finding the best promotion, made larger by threshold-based and ordinary offers. Xiaoming created PromotionCalculator to expose methods for selecting the best offer and calculating the best price:

@interface PromotionCalculator: NSObject

+ (CGFloat)calculateAmount: (CGFloat)amount;
+ (Promotion *)bestFullPromotion: (CGFloat)amount;
+ (Promotion *)bestDiscountPromotion: (CGFloat)amount;

@end

@implementation PromotionCalculator

+ (CGFloat)calculateAmount: (CGFloat)amount {
    Promotion * bestFullPromotion = [self bestFullPromotion: amount];
    Promotion * bestDiscountPromotion = [self bestDiscountPromotion: amount];
    if (bestFullPromotion.synchronize && bestDiscountPromotion.synchronize) {
        return [bestFullPromotion discountAmount: [bestDiscountPromotion discountAmount: amount]];
    } else {
        return MAX([bestDiscountPromotion discountAmount: amount], [bestFullPromotion discountAmount: amount]);
    }
}

+ (Promotion *)bestFullPromotion: (CGFloat)amount {
    PromotionManager * manager = [PromotionManager sharedManager];
    return [self bestPromotionInPromotions: [manager fullPromotions] amount: amount];
}

+ (Promotion *)bestDiscountPromotion: (CGFloat)amount {
    PromotionManager * manager = [PromotionManager sharedManager];
    return [self bestPromotionInPromotions: [manager discountPromotions] amount: amount];
}  

+ (Promotion *)bestPromotionInPromotions: (NSArray *)promotions amount: (CGFloat)amount {
    CGFloat discount = amount;
    Promotion * best = nil;
    for (Promotion * promotion in promotions) {
        CGFloat tmp = [promotion discountAmount: amount];
        if (tmp < discount) {
            discount = tmp;
            best = promotion;
        }
    }
    return best;
}

@end

After distributing this logic to the appropriate places, Xiaoming is surprised to find that other modules need only a few lines for their calculations:

- (void)viewDidLoad {
    [PromotionRequest requestPromotionsWithComplete: ^(PromotionManager * manager) {
        _discountAmount = [PromotionCalculator calculateAmount: _order.amount];

Closing thoughts

This is my second article on MVC, and I still want to emphasize that MVC has real limitations that emerge in large projects—though I am a novice who has not developed a large one. If your project's layers are well separated, do not hesitate when an architectural change becomes appropriate. But if the problem is merely repeated useless code or all logic stuffed into controllers, changing architecture only redistributes the mess.
