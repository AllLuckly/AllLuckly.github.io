Wider text need not be moving. ASS t transforms animate eligible style properties using milliseconds relative to the event start. Build two horizontal-scale controls, calculate intermediate values and observe the available iCouldPlay path. External authoring is not an animation editor claimed for the player.

Prepare a twelve-second source and initial style

Retain an owned clip at least twelve seconds long, duration and subtitle path, preserving prior captions. Fix the640×360 script, font size 36 and initial horizontal/vertical scale 100%. Record absolute cue seconds, relative milliseconds, horizontal scale and observed state separately. Hold fitting, orientation and playback speed fixed; volume or video speed is not a substitute for subtitle styling.

Save complete linear and squared-progress cues

Events 1–5 and6–10 use identical wording and placement. Both change horizontal scale 100→150 over relative0–2000ms; acceleration is 1 and2 respectively. Save UTF-8 transform.ass and reopen, preserving ASCII syntax. Vertical scale stays fixed and no move is specified. The t tag does not invent a trajectory or endlessly repeating animation.

Add the event start to the transform window

The first transform occupies media1–3s and holds at target during 3–5. The second changes at 6–8 and holds8–10. Identical relative millisecond values correspond to absolute times five seconds apart. List all intervals. The target scale does not keep text onscreen after its event; entering another event does not inherit the former event’s progress.

Calculate both intermediate scales independently

At halfway through the window, fraction is 0.5. Acceleration1 gives100+50×0.5=125%; acceleration2 gives100+50×0.25=112.5%. These occur at media2s and7s for the respective events. They are scale percentages, not measured device-pixel widths. Acceleration2 changes progress shape without halving the total duration.

Observe start, middle and hold by sequential playback

Load through available controls and play sequentially, checking text first and then each start/change/hold. Pausing can assist, but uncertain timing needs an observation range rather than an invented measured width. Font differences undermine comparison before they establish a curve error. Record text loading and animated scale separately as observed, absent or unperformed.

Recalculate quarter and three-quarter progress

At quarter progress, scales are112.5% and103.125%; at three quarters,137.5% and128.125%. Both reach150% at the window end. The squared curve is slower initially, not unable to reach target. This model uses positive parameters; it establishes no behaviour for invalid ones. Keep calculations separate from timestamp uncertainty and actual screenshots. A separate1000–3000ms window moves the first change to media2–4s. At2.5s its fraction is now one quarter, giving112.5% and103.125%;do not reuse the original window’s progress.

Diagnose initial value, scope and eligible tags

For an initially wide line, check fscx100 and copy identity. For no change, inspect t scope, milliseconds and rendering capability. Inserting an ineligible tag such as org is not a useful compatibility test. Unexpected height calls for checking fscy/font size. Change one condition and retain failures; identical wording does not replace an initial-style/font record.

Reopen and deliver the time/scale ledger

Reopen and reselect the original, checking both intervals and holds before restoring prior captions. Deliver initial style, relative/absolute windows, three progress examples, actual observations and version. A computed112.5% is not a physical-device measurement. Recalculate changed targets/windows rather than reuse times. No video encoding, recording speed or audio pitch was changed.
