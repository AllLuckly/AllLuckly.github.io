Preserve evidence of a working input state and restore language, layout or appearance separately, without assuming automatic backups or a universal reset.

1. Start with a real change and working baseline

Use a real setting change you want to recover from, preserving current state, recent changes and the last working record. Without a problem, establish a baseline and mark recovery unperformed rather than disrupt important input. A baseline identifies ordinary typing, Jianlai, language/layout and appearance; a store screenshot is insufficient. Preserve documents/themes instead of uninstalling or clearing system keyboards, which would remove the comparison needed for restoration.

2. Classify language, layout and appearance changes

List input language, Chinese layout, theme/font separately, adding sound/haptics only if changed. Record known original/current values and symptoms, leaving forgotten values unknown. Separate app-interface from input language and preview from active keyboard. This external ledger is not an automatic configuration history or complete export. It chooses the next restoration condition rather than inventing one reset for every problem.

3. Preserve a fallback in an ordinary note

Check a controlled ordinary note and retain the system-keyboard fallback for nonsensitive recording if needed. A working fallback does not repair Jianlai, but avoids repeated trials in real messages/account forms. System substitution in secure/special fields needs boundary diagnosis, not an assumption of lost configuration. If lists/states are unclear, retain records/fallback rather than toggle permissions blindly. This restores existing choices without bypassing host or secure-input restrictions.

4. Restore one known language or layout condition

If language/layout differs from baseline, restore one known changed condition and type the same short marker. Do not also change theme/sound and lose causal clarity. With an unknown original, an identifiable working choice can establish a new baseline, but is not exact restoration of the old configuration. Check candidates and commitment separately and retain observations. Do not invent recovery of unavailable custom schemes or unpublished dictionaries.

5. Restore appearance in a separate input-stable round

After confirming basic input, restore one known appearance value while retaining other conditions. Check preview and active keyboard separately. Similar editor colours do not prove every original parameter returned. If an old theme is unknown, record a readable replacement as such rather than automatic backup restoration. Preserve images/themes and note read-only/unavailable fields. Keyboard size and document styling differ; unchanged document text does not alone refute restored keyboard appearance.

6. Keep feedback and text evidence distinct

If feedback actually changed, save prior recovery before restoring one known sound/haptic condition. Record heard, felt and inserted results separately. Silence is not failed typing, and text does not prove haptics. Retain device/system limitations and leave untouched feedback alone. No universal vibration target or Full Access/reinstall prerequisite is prescribed. Follow actual explanations and choices, leaving data-processing mechanisms unknown rather than inferring them from a switch.

7. Retain a stopping point and useful evidence

For repeated failure under one clear condition, compare symptoms and retain version, host, language/layout and a nonsensitive sample instead of reverting everything indefinitely. Continue the verified fallback while keeping unresolved work pending rather than deleting documents for a pass. Redacted state records suffice for help, not passwords/chats/private images. One changed condition makes results explainable; changing everything and obtaining a working state does not identify one unique defect.

8. Deliver the recovery ledger and actual final state

Verify saving/reopening in the ordinary note and record actual final keyboard, language/layout, appearance and feedback checked, preserving the original baseline. Separate exact restoration, usable replacement and unknowns rather than calling every new choice the old configuration. Retain fallback access and exclude unperformed resets/synchronisation/cross-device recovery. Update external baselines before future changes. This is a traceable recovery process, not an automatic backup tool or device-wide repair certification.
