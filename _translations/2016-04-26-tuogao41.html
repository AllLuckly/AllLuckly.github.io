MVVM

MVVM: Model-View-ViewModel
MVVM is an evolution of MVC. It decouples business logic from the VC into a ViewModel, substantially slimming the VC down.

Let the code explain it!

Implement a simple sign-in check:

Create LoginViewModel for logic, LoginModel for data only, and LoginViewController. I am not using a separate LoginView here, so beginners can focus on decoupling through the ViewModel.

If you already understand all this, go directly to Wzxhaha/RandomerFramework, which is the basic architecture of my independent project Randomer—SubClasses+Protocol+MVVM+RAC—and its sign-in and registration module. Also, thanks to This article by 王隆帅 opened the door to a new world for me.

Add a method to LoginModel.

//.h
- (instancetype)initWithUserName:(NSString *)username password:(NSString *)password;

@property (nonatomic,copy,readonly)NSString * username;
@property (nonatomic,copy,readonly)NSString * password;



//.m
- (instancetype)initWithUserName:(NSString *)username password:(NSString *)password {
    if (self = [super init]) {
        _username = username;
        _password = password;
    }
    return self;
}


There is little to explain here: simply add an initializer to the Model.

Add a method to LoginViewModel.

#import "PersonModel.h"

- (instancetype)initWithPerson:(PersonModel *)person;
@property (nonatomic,assign,readonly)BOOL canLogin;
- (instancetype)initWithPerson:(PersonModel *)person {
    if (self = [super init]) {
     //在这做你绑定model后的处理
      _canLogin = [self valiCanLoginWithUserName:person.username password:person.password];
    }
    return self;
}

- (BOOL)valiCanLoginWithUserName:(NSString *)username password:(NSString *)password {
    if (username.length && password.length) {
        return YES;
    } else {
        return NO;
    }
}


Add an initializer that binds a Model to the ViewModel, along with a method to determine whether the account and password are valid.

The VC or View can then obtain the checked result directly like this:

PersonModel * person = [[PersonModel alloc]initWithUserName:@"10" password:@"10"];
PersonViewModel * viewModel = [[PersonViewModel alloc]initWithPerson:person];

NSLog(@"%d",viewModel.canLogin);


The difference is small for simple features, but MVVM has major advantages when dealing with complex logic.

I will also discuss ReactiveCocoa. A main reason I recommend MVVM so strongly is how well RAC fits with it!

ReactiveCocoa

RAC combines functional and reactive programming. If those ideas are unfamiliar, see my WZXProgrammingIdeas

RAC's main value is observing events, which it calls signal streams, and receiving those signals through block callbacks. It uses blocks extensively, so use @weakify(self) and @strongify(self) properly.

Why do RAC and MVVM fit together so well?

MVVM moves methods into a ViewModel, but the VC or View must still call them. The logic deciding when to make those calls can remain complicated.

RAC solves this by observing events and calling ViewModel to perform the logic.

For example:

   [[_registerBtn rac_signalForControlEvents:UIControlEventTouchUpInside]subscribeNext:^(id x) {
        @strongify(self)
        [self.viewModel toRegisterWithType:Register];
    }];

    [[_loginBtn rac_signalForControlEvents:UIControlEventTouchUpInside]subscribeNext:^(id x) {
        @strongify(self)
        [self.viewModel loginWithUserName:self.usernameTextField.text password:self.usernameTextField.text Success:^(id response) {
        } failure:^{
            SHOW_ERROR(@"错误", @"账号或密码错误")
        } error:^(NSError *error) {
            SHOW_ERROR(@"错误", @"网络连接失败")
        }];
    }];


RAC observes the sign-in and registration buttons, keeping the code concise and the structure compact.

A chainable networking framework

Why wrap networking in WZXNetworking?

This framework is remarkably tolerant of errors.

 [[WZXNetworkManager manager].setRequest(@"http://192.168.1.40:8001").RequestType(POST).HTTPHeader(nil).Parameters(nil).RequestSerialize(RequestSerializerHTTP).ResponseSerialize(ResponseSerializerJSON) startRequestWithSuccess:^(id response) {

        NSLog(@"success");
    } failure:^{

        NSLog(@"failure");
    }];


Here, everything except .setRequest(url) and startRequestWithSuccess failure is optional.

You can do this:

[[WZXNetworkManager manager].setRequest(@"http://192.168.1.40:8001") startRequestWithSuccess:^(id response) {

        NSLog(@"success");
    } failure:^{

        NSLog(@"failure");
    }];


Chaining is particularly useful when there are many parameters and choices, or when they are likely to change. Modifications are easy: just add or change a method.

For example:

A centralized API wrapper would look like this:

- (void)GET:(NSString *)url
        parameters:(id)Parameters
        success:(SuccessBlock)success
        failure:(FailureBlock)failure;


If you need a Version property to check API versions, what can you do? Rewrite the method with a Version parameter, then update every network request that calls it.

We will leave a distributed API wrapper out of this comparison…

GeneralAPI *apiGeGet            = [[GeneralAPI alloc] initWithRequestMethod:@"get"];
apiGeGet.apiRequestMethodType      = RequestMethodTypeGET;
apiGeGet.apiRequestSerializerType  = RequestSerializerTypeHTTP;
apiGeGet.apiResponseSerializerType = ResponseSerializerTypeHTTP;
[apiGeGet setApiCompletionHandler:^(id responseObject, NSError * error) {
    NSLog(@"responseObject is %@", responseObject);
    if (error) {
        NSLog(@"Error is %@", error.localizedDescription);
    }
}];
[apiGeGet start];


Is this structure too loosely connected?

Now replace it with WZXNetworking.

All we need is another method and instance variable, then append .method() to the existing call.

- (WZXNetworkManager * (^) (id some))method {
  return ^WZXNetworkManager (id some) {
     self.XXX = some
     return self;
  }
}



[[WZXNetworkManager manager].setRequest(@"http://192.168.1.40:8001").method(some) startRequestWithSuccess:^(id response) {

        NSLog(@"success");
    } failure:^{

        NSLog(@"failure");
    }];
