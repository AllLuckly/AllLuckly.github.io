When entering a table, keyboard characters, the focused cell and table structure are three different layers. Jianlai enters text, while available table controls in Apple Notes belong to the host. Use a small table with fictional items and no private information to check whether words land in intended cells, then distinguish table structure from plain text in a copy.

Create a test note

Create an editable note in an iPhone Notes account that supports tables. Confirm Jianlai is enabled in system keyboards and select a Chinese or English input mode actually visible. Record system version, Notes account and keyboard layout. Do not use existing bills, real inventory, addresses or an unbacked-up worksheet. If the account or system lacks a table entry, mark the step not tested rather than disguising spaces as a table in a formal document. Apple says the first line can become the note title, so enter “Practice items” and a newline.

Create and confirm a two-dimensional structure

Use the Add Table control actually visible in Notes. If the initial table differs from two rows and two columns, follow the host's actual row and column controls. The target is two columns and three rows; do not enter real information. If adding or selecting rows and columns is unclear, stop and preserve the blank test note rather than deleting other content to force the structure. You can draw a two-column, three-row grid on paper and label its first and second columns, then inspect the screen boundaries. The paper is a positioning aid, not evidence that Notes created the table. Do not infer sufficient rows solely from a Return key on the keyboard. Table and row controls belong to Notes, not keys Jianlai promises to provide.

Enter the first-row labels

Select the first row, first column, confirm the insertion point and enter “Item” with Jianlai. Select the first row, second column and enter “Quantity”. Verify the labels occupy different cells rather than both landing in one. If necessary, tap outside and return to inspect; an active candidate is not committed text. The host may expose different controls when tapped. Follow the visible interface rather than assuming a particular key always moves to the next cell.

Enter the second row

Select row two, column one and enter “Paper”; then enter “2” in row two, column two. Confirm focus moved from the left cell to the right before typing the digit. If the digit remains in the left cell, stop and correct it locally before proceeding. This is a fictional quantity, not real inventory. Observe text, cell boundaries and focus separately: a visible keyboard alone does not establish that the target cell is selected.

Enter the third row and inspect each cell

Enter “Pen” in row three, column one and “5” in column two. Compare row by row with the reference: “Item / Quantity”, “Paper / 2”, “Pen / 5”. Slashes here denote column boundaries and should not be typed into the table. Inspect actual text and position in each cell for extra spaces or repeated digits. If a cell is visually clipped, use the host's available viewing method rather than declaring data lost from a truncated display.

Preserve a baseline before copying

To avoid overwriting the only copy, use available system controls to copy the whole test table into a new private-data-free note, then verify every row and column. If the whole table cannot be copied, first record each cell's text and location as a manual baseline; a screenshot is not an editable backup. Do not copy real data into an untrusted app. If the copied structure cannot be confirmed, record unknown and retain the source rather than cleaning up.

Edit one value locally

Return to the source table. Select “5” in row three, column two and, once the selection is clear, replace it with “6” using Jianlai. Check that the cell contains only 6, “Pen” remains to its left, and the earlier “Paper / 2” row is unchanged. If selection crosses cells, cancel and reposition first. Do not assume a single undo restores only one digit. Keep before-and-after tables in the record so the actual target change is visible.

Compare the copied result

Check whether the earlier copy still shows “5” while the source shows “6”. This is the current observation, not proof that every copy method creates an independent copy. If testing a different host or paste method in a new test document, separately record whether rows, columns, text and order survive; do not presume a table always becomes plain text or retains formatting. Mark uncertain steps not tested instead of manually filling missing data to make copying appear successful. For example, if the destination only shows three text lines without visible cells, record visible words and unconfirmed structure separately. If cells remain visible, still check each cell against the source. Copying is not synchronization and one test does not establish automatic updates on another device.

Troubleshoot and finish

If text lands in the wrong cell, inspect actual focus and selection, then compare the intended position. A Chinese keyboard being visible does not establish correct host focus. If table controls are missing, check account and system support or use a supported test environment; do not buy software, change permissions or casually alter account settings for the exercise. Keep or delete the test notes as you prefer and restore your prior keyboard selection. This guide uses Apple's public information and does not claim a step-by-step test on a personal device.
