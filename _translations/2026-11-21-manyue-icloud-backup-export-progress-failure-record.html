Record a personal comic library’s pre-export state, then check progress feedback, result identity and recovery evidence separately.

Record a pre-export sample

Choose your own device and a comic that opens, recording its chapter and a nonsensitive reading anchor. Confirm another source for the original comic and preserve existing reading records; the actual backup description determines whether comic files are included. Stop if you lack authorization or cannot preserve the current state.

Check the system account and prerequisites

In system settings confirm this is your own Apple account and iCloud is available, and inspect actual network and storage messages. Do not include account details, codes, server credentials or complete comics in feedback. System sign-in does not prove an app export succeeded or that space is sufficient. Address an actual capacity warning rather than retrying repeatedly.

Read the actual export entry and prompt

Find the iCloud backup export entry visible in the installed ManYue version and read its explanation and data scope. Public 2.0.6 notes mention export progress and failure messages; if the entry is missing or its effects are unclear, record that and stop. Do not equate an iCloud sync switch or system device backup with this app export.

Prepare a before-and-after checklist

In a private device note, make columns for item, visible state before export and observation afterward. Items can include actual backup names and dates, whether the sample comic opens and its chapter position; omit accounts and private addresses. If the list is initially empty, record no copy observed rather than asserting no old cloud data exists. Keeping names and identifiable times helps distinguish a new export from an entry that was already present.

Details to record from the export prompt

Before any actual action, check the stated destination and export scope. If the interface gives no file list, record that it was not provided. Do not substitute the system device-backup time for the app’s cloud-copy time.

Observe one export attempt

When the prompt is understood and you are authorized, start one export and record the start time, visible stage and actual feedback. A percentage, spinner and closed window are interface signals, not standalone proof of a recoverable copy. On failure retain a redacted message and stage instead of repeated rapid taps. Mark the result unperformed if no export was started.

Identify the result and inspect integrity separately

After the export, look for the actual copy identifier, time and integrity feedback offered, comparing them with the pre-export list. If no explicit result is available, record it as unknown. The release notes mention backup integrity checking, but do not infer its coverage of every file or claim a completed restoration. Do not overwrite the only existing copy or delete source comics or records to test it.

Separate progress from completion

If a percentage is available, note the start, one intermediate observation and last visible value without watching continuously. The percentage may measure the stage described by the interface; do not convert it into a claim of durable cloud storage or every book copied. If the app enters the background or the network drops, record the action and time and use actual feedback to decide whether to continue. Do not assume background completion on every system. Without an explicit result, mark the export unknown.

A useful check need not perform a restore

This exercise delivers an export observation; it does not require immediate recovery. When a new entry can be identified, record its interface identifier, time and app-displayed state. Whether it can actually be restored requires a separate check after protecting existing data. Even an integrity-pass message must be interpreted within the scope the app explicitly states. If old and new copies cannot be distinguished, retain both and pause restoration; provide the maintainer only redacted version and message details.

Fill an observation sheet using a simulated failure

To protect real data, first practice on paper with a fictional record: device D1, existing backup entry A, start time 10:00, feedback “network unavailable” and final state “unknown.” This is a table exercise, not an instruction to disconnect a device or a claim of an actual failure. Replace it with information actually shown during a real operation, classifying the state as not started, in progress, success message, failure message or indeterminate. If only progress appears with no final message, retain that last state rather than guessing success after waiting. Compare names and timestamps with the pre-export list, and label only a distinguishable new entry as a candidate copy. Record the app’s integrity feedback and any unperformed restoration separately. A later reviewer can then see the evidence without treating one green icon as proof that all data is recoverable.

Record a failure and next step

Distinguish unavailable network, account prompts, storage messages and app errors. Keep the time, completed stage and redacted actual message. Change one confirmed condition before deciding whether to retry; do not blame comic format without evidence. Return to the same comic to verify chapter and original, then separate confirmed observations from untested items. No actual export, device operation or cloud restore is claimed.
