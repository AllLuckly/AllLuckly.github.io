3. A simple way to find a font name

We found FZLBJW–GB1-0 by comparing font lists above, but there is an easier way. Find the ttf in Finder and double-click it. Double-clicking it in Xcode does not have this effect. The system opens it in Apple's Font Book, as shown below.


We can now see the font-family name, FZLiBian-S02S. Search for that family in the console output listing all fonts to find the specific font name.


This is much simpler than the earlier approach.

4. Further considerations

The example above changes fonts successfully, but it raises a question. There are only two simple controls here; what if there are many? You could apply the same method one by one, which is manageable for controls created in code. But with xibs, must you create outlets for every otherwise unneeded display-only label or button just to change the font? That would be inefficient, especially in a large, partly completed project. This approach clearly will not scale.
This uses the runtime methods class_addMethod, class_replaceMethod, and method_exchangeImplementations together with the behavior of + (void)load. I will discuss + (void)load later; if it is unfamiliar, you can also look it up first. Here is the code:

//
//  UILabel+FontChange.m
//  LiquoriceDoctorProject
//
//  Created by HenryCheng on 15/12/7.
//  Copyright © 2015年 iMac. All rights reserved.
//

#import "UILabel+FontChange.h"
#import <objc/runtime.h>

#define CustomFontName @"FZLBJW--GB1-0"

@implementation UILabel (FontChange)

+ (void)load {
    //方法交换应该被保证，在程序中只会执行一次
    static dispatch_once_t onceToken;
    dispatch_once(&onceToken, ^{
        //获得viewController的生命周期方法的selector
        SEL systemSel = @selector(willMoveToSuperview:);
        //自己实现的将要被交换的方法的selector
        SEL swizzSel = @selector(myWillMoveToSuperview:);
        //两个方法的Method
        Method systemMethod = class_getInstanceMethod([self class], systemSel);
        Method swizzMethod = class_getInstanceMethod([self class], swizzSel);

        //首先动态添加方法，实现是被交换的方法，返回值表示添加成功还是失败
        BOOL isAdd = class_addMethod(self, systemSel, method_getImplementation(swizzMethod), method_getTypeEncoding(swizzMethod));
        if (isAdd) {
            //如果成功，说明类中不存在这个方法的实现
            //将被交换方法的实现替换到这个并不存在的实现
            class_replaceMethod(self, swizzSel, method_getImplementation(systemMethod), method_getTypeEncoding(systemMethod));
        } else {
            //否则，交换两个方法的实现
            method_exchangeImplementations(systemMethod, swizzMethod);
        }

    });
}

- (void)myWillMoveToSuperview:(UIView *)newSuperview {

    [self myWillMoveToSuperview:newSuperview];
//    if ([self isKindOfClass:NSClassFromString(@"UIButtonLabel")]) {
//        return;
//    }
    if (self) {
        if (self.tag == 10086) {
            self.font = [UIFont systemFontOfSize:self.font.pointSize];
        } else {
            if ([UIFont fontNamesForFamilyName:CustomFontName])
                self.font  = [UIFont fontWithName:CustomFontName size:self.font.pointSize];
        }
    }
}

@end

What if some views should change font and others should not? A simple approach is to use a tag. For example, I assign a label the arbitrary tag 10086 to exempt it from the font change.


Result when run


Note:

1. For a control created in code whose font should remain unchanged, set its tag to 10086 when creating it.
2. One line in the code above is commented out: 

//    if ([self isKindOfClass:NSClassFromString(@"UIButtonLabel")]) {
//        return;
//    }


This line was originally used to leave button-title fonts unchanged. Decide which control types should change and which should not. To preserve button fonts, uncomment this line.
3. For a control created in a xib whose font should remain unchanged, set its tag to 10086 in the xib. Do not wait until - (void)viewDidLoad after loading. This is again due to the behavior of + (void)load.

Before a program's main function runs, after its libraries load into the runtime, the runtime invokes +load on the classes and categories added to it. You can easily verify this with log statements.
If both a superclass and subclass have +load methods invoked, the superclass always runs first. The system handles this automatically; the subclass does not need to call [super load] explicitly. This is only a brief explanation. Consult the official documentation for more detail.
