Where the device permits, place two widgets of the same available kind and record each instance’s actual fields and observation times against one playback session. Deliver a ledger separating a static entry, any displayed track information and real sound. No play buttons, fixed refresh deadline or two independent players are promised.

1. Confirm the installed app and available widgets

调调 1.0.1 publicly adds Home Screen widgets, without enumerating all sizes, fields or interactions. First confirm an actual 调调 option in your device’s widget gallery, noting installed version and available kind while preserving the existing Home Screen. If absent or not updated, stop at preparation rather than claiming an addition from promotional imagery. One kind is sufficient; invent no cover, server or lyric configuration. Assign external identifiers A and B for the ledger, without requiring widget renaming. Establish a real addable option before creating two instances; two screenshots of one changed widget do not establish simultaneous instances.

2. Put matching instances in distinguishable positions

Use the real system flow to place two instances of the same available kind and size in distinguishable locations. If space or system conditions prevent the second, retain a single-instance result and the limitation instead of removing important widgets. This compares instances, not sizes or configurations simultaneously. If differences are unavoidable, record them rather than attribute all changes to refresh. Confirm both actually exist on the Home Screen; gallery previews do not count. Another widget does not imply another audio session, and its image does not establish current sound. A kind without track information can only be checked for fields it actually supplies.

3. Inventory each instance’s actual fields

For A and B separately record an app entry, title, artwork, state text or whatever actually appears. Mark absent fields not applicable instead of assuming a Pause button from the widget name. A static launcher should be recorded as such, with dynamic-title comparisons not applicable rather than invented. If an identifiable opening action exists, check its app destination separately; otherwise do not tap guessed areas. Visible fields and interactive capabilities need separate columns because a play graphic is not proof of an available button. Put instance labels and observation times in an external ledger, without unpublished internal identifiers or developer debugging tools.

4. Establish an in-app paused-track baseline

Prepare two distinguishable owned local audios with different titles and opening phrases, long enough for the observation window, for example three minutes each, verifying actual properties first. Position track A at its recognizable beginning in 调调, pause and record title, silence and visible position, then inspect both Home Screen instances. Copy displayed track information only if supplied; otherwise record the entry state. Pausing and immediate widget text changes are separate checks. Old artwork does not prove ongoing sound. Two instances pointing to the same app collection do not establish two playback tasks; verify the known app session rather than infer audio from Home Screen graphics.

5. Separate playback and track-change windows

Play track A in the app, verify sound and return home. Record A/B fields at self-selected zero, thirty and ninety-second observation points. This is a sampling schedule, not a ninety-second refresh guarantee. Then run a separate track-change window: confirm track B’s title and sound in the app and inspect both instances at the same relative points. Use audio long enough to avoid natural ending; record any ending that occurs. Do not simultaneously change theme, network or widget size. A kind without dynamic fields stays not applicable rather than failing to show track B. Each record needs an actual state and approximate time, not the same screenshot reused as later evidence.

window 1: app track A playing; observe widget A/B at 0, 30, 90 s
window 2: app track B playing; observe widget A/B at 0, 30, 90 s
Times are observation choices, not refresh deadlines.

6. Separate platform refresh principles from observations

Apple’s WidgetKit documentation explains that widgets do not run continually and system conditions and budgets influence updates. Multiple instances are not thereby guaranteed identical displays at the same instant. This is platform context, not a published fixed polling interval for 调调. If one changes before the other, record order and observation range without diagnosing two caches or servers. If neither changes, first check whether the kind is a static launcher. Widget updates and actual playback are different clocks; sound still needs direct checking. Any measured refresh delay is specific to this round, not an app guarantee copied from typical platform behavior.

7. Diagnose instance identity and static/dynamic scope

For differing instances, first verify matching kind/size and that B is not another app’s widget, then actual fields. For a mismatched dynamic title, confirm the current in-app track and retain widget state and time instead of repeatedly removing and adding until a favorable image appears. System editing or removal can be tested separately, but a newer display after readdition does not establish the earlier internal cause. Invent no force-refresh button or developer reload action as a user repair. Deliver uncertainty and reproducible conditions rather than equating unchanged appearance with failed playback. One opening action does not make every graphic interactive.

8. Restore the Home Screen and deliver both ledgers

Save locations, kinds, fields, observations and in-app baselines, marking static or unperformed dynamic items. To restore the Home Screen, remove only extra instances added for this exercise through explicit system controls, not the app or existing data, and verify removal. Restore playback and record the final state; unperformed reopening stays pending. Explain two presentation instances, the source of actual sound and update behavior observed only in this round. This does not test every size, background duration or interaction. New app/system versions require fresh scope checks rather than treating the sampling schedule as a long-term refresh promise.
