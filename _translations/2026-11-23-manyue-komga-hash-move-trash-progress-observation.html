After moving a comic file, server record restoration and matching Manyue+ progress require separate checks.

Separate file identity and reading records

Komga documents that file hashes and the trash can help preserve metadata, read progress, read lists and collection relationships when files move or are renamed. Without a file hash, data cannot be restored from a move or rename on that basis. A server identity mechanism is not a promise that Manyue+ synchronizes every record; inspect client display and progress separately.

Prepare an isolated sample and backup

Use a Komga test library you manage or are authorized to access. Prepare a self-made or authorized small CBZ copy with at least three distinguishable images. The administrator first backs up files and database under normal practice and checks the test-library settings. Do not use the only original or production reading history. Without administrator access, a reliable backup or permission, stop at preparation and move nothing.

Confirm hash and trash conditions

Ask the administrator to consult the current Komga documentation, confirm the test book has a usable file hash, and inspect whether the test library automatically empties trash after each scan. The documentation warns that automatic emptying prevents simple recovery from mistakes and interferes with cross-library moves. Do not enable it or empty trash for this exercise. If hash or recovery conditions cannot be confirmed, stop and mark the test not performed.

Establish a reading baseline

Open the test book in the Komga web interface with the test account. Record title, series, page count, first-page marker and progress. If that account already has a read list or collection relationship, record its identity and ownership without modifying production lists for this exercise. Connect Manyue+ to the same server and account and record the same book’s displayed title, readable pages and actual progress. Report any existing difference honestly.

Have the administrator move the test copy

With permission, move only the test CBZ within the same test library from one scannable location to another, keeping its bytes and filename unchanged. Folder organization must follow the current Komga documentation and library configuration. Record start, destination, time and file size. Do not extend the operation to production libraries or cross-library migration. Before moving, reconfirm that the backup is recoverable and trash will not empty automatically.

Wait for scanning and inspect the web

The administrator scans the test library through the normal current-version procedure and waits for completion. On the web, identify the moved book using its first-page marker, page count and series. Record whether the entry reappears, its original metadata, progress and any previously recorded list relationships separately. If a hash is missing or restoration is incomplete, do not presume permanent data loss; have the administrator inspect the state and pause further renaming and cleanup.

Check the actual Manyue+ result

In Manyue+, use the same source and account, re-enter the relevant series through the actual interface and inspect book, cover, first page, page count and progress. If the book appears but progress differs, record web and app results separately. Server progress preservation is not proof of automatic client synchronization. If no entry appears, check account, source, test library and server scan status before deleting local shelves or reimporting a sole file.

Distinguish moving from changing content

This experiment moves a copy without changing its bytes. Recompressing the CBZ or changing images or embedded metadata adds a content change, so its hash-matching result cannot be compared directly to a pure move. Restore a backup and keep a separate record for a different experiment. Equal filenames do not prove equal content, and equal file sizes do not prove byte equality; the administrator confirms actual hashes using a trusted procedure.

Handle missing restoration

Preserve the current test library and trash; do not empty or batch-delete them. The administrator checks whether the original file exists, the hash was computed, the scan finished and the file entered the correct library. If the web recovered but Manyue+ did not display the book, record version, time, source and actual message without asserting a cache or sync mechanism. Exclude server address, account, comic content and tokens from support handoff.

Check series identity after the move

Komga books normally belong to series directories. Moving into another test series can change visible grouping even when file bytes are unchanged; it is not the same as retaining the original series view. Have the administrator confirm the destination and expected series, then record book identity, series name and read-list relationship separately. If only an in-series rename is permitted, use that single approved operation and note the difference rather than changing folder and filename together.

Record scan start and completion alongside each observation. If scanning is ongoing, mark waiting rather than treating the old interface as final. Pause after an unexpected result so the administrator can assess backups and existing trash. Do not rebuild the database or send its raw contents to support without authorization.

Restore and summarize

The administrator restores the test file location or handles the test copy according to backup and normal procedure, then confirms production comics and records are untouched. Include baseline, moved and restored file identity, web and app states, and unperformed steps in the results table. This public-documentation guide claims no private-server connection or physical-device test.
