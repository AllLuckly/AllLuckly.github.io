Retain separate provenance for an imported copy and server item instead of treating one playable path as proof of the other.

1. Prepare two authorised source paths

Choose authorised music available through a confirmed compatible server and as a legitimate importable source file you possess. Service-only listening permission does not supply a local file; choose another sample or leave local preparation pending. This task neither extracts protected content nor assumes a server-download button in 调调. Record server provenance and source-file location separately even when titles match. Preserve both originals and service: the goal is path verification, not moving a private collection elsewhere.

2. Check editions rather than names alone

Compare title, artist, album, duration and audible anchors, retaining only verified fields. Same-name live, rerecorded or edited versions are not automatically identical samples; different filenames can still share content. Without edition evidence, compare two identifiable sources rather than claim byte equality. This task measures neither encoding equivalence, audio quality nor internal deduplication. It establishes which entry was selected for each playback and how to trace it back to its origin.

3. Complete the local-import path separately

Import the legitimate file through the existing flow, find it specifically in local music and verify metadata and opening sound. Label that local identity A instead of substituting a same-name server cover. If it already exists, retain duplicate handling and inspect the existing A rather than delete it to force a count. Importing covers this device only. Another phone’s copy does not establish local storage here, and local playback does not prove the server account remains valid.

4. Record the remote entry and opening separately

With normal connectivity, re-find the server entry B and record service identity/opening feedback. Verify its sound/edition instead of treating continuing local A as B’s playback. Pause A first, select B through a clear path and then listen. If no provenance badge exists, record the identifiable browse path rather than invent a hidden label. Remote opening establishes this access round, not a local-library download or automatic merging of playback history across sources.

5. Use offline conditions to check the identified local A

Save both online results before creating a clear reversible offline condition when communication needs permit. Reselect A from local music and verify its identity/anchors. Continuing a few seconds of remote playback does not establish complete local storage. Do not clear caches or delete server data to manufacture differences. Record disconnection scope and limit unclear results. A playing verifies this local path and observed positions under current conditions, not offline readiness of all server tracks. Keep lyrics, remote art and audio evidence separate.

6. Avoid guessing remote caching from offline behaviour

For an optional offline B observation, record the actual reopening path and outcome without predicting certain failure or success. Buffered passages, listing information and a complete local import can behave differently; no universal cache policy is published here. A sounding passage is not a complete saved track, and an empty list does not mean server originals were deleted. Mark the optional round unperformed if not done. A’s evidence must not be copied into B’s row; both paths require separate observations.

7. Restore networking and diagnose by path

Restore the original network and recheck A and B independently. If A works but B is inaccessible, inspect service address, access and account scope. If both items are silent, inspect output/tracks; if only editions differ, inspect provenance. These are not all synchronisation errors, and sign-out/reinstallation does not replace a small control. Change one condition per round and preserve online, offline and restored results. Do not prescribe unpublished cross-source progress merging, automatic downloads or cross-device queues.

8. Deliver two source records rather than one name

Confirm networking is restored and source file/server data remain preserved. Save each location, edition evidence, opening action and actual online/offline/restored outcomes. Explain why same name, same edition and stored locally are different claims, keeping unresolved items explicit. Re-establish both paths after device, service or original changes instead of relying on old artwork. This is traceable local-versus-remote verification, not completed testing of every cache, synchronisation feature or private catalogue.
