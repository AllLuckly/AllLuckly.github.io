分别记录健康检查、网页登录、云映列表和指定短片播放，避免将服务状态当成播放结果。

云映打不开 Jellyfin 时，一条服务器健康检查可以帮助分辨服务是否回应，但不能代替账号登录、资料库访问或实际播放。本练习把四个结果分开记录，避免看到一个 HTTP 状态就断言视频一定能播。

## 准备获准的检查条件

选择自己管理或已获授权的 Jellyfin 服务，以及管理员允许访问的检查入口。准备同一账号可观看的一段短片，并记录云映所在设备、网络和时间。没有检查权限、管理员尚未提供入口或服务器正在维护时，停在记录阶段，不扫描陌生地址，也不为练习公开端口。保留原服务器和应用配置。

## 先了解健康检查的范围

Jellyfin 官方文档说明，`/health` 用于检查底层服务，目前成功时返回 HTTP 200，并核对 HTTP 与数据库连接。服务器启动和迁移期间结果可能不符合预期。这个结果不等于用户账号有权限，也不验证所有视频文件、转码、音轨或云映客户端。由管理员确认当前版本及正确地址；反向代理可能限制该入口，不能擅自调整规则。

## 建立脱敏记录

写四行：服务健康检查、网页账号与资料库、云映列表、指定片段播放。每项分别填写检查时间、成功、失败或未执行。用“家庭服务器 A”代替真实域名；不要记录账号密码、令牌或含签名的播放链接。若管理员只允许他本人做健康检查，请他提供状态和检查时间，不必索要私有地址。

## 检查服务响应

由有权使用终端的管理员，在其允许访问的网络运行官方提供的 `curl -i` 检查，地址使用管理员确认的实际健康端点；示意 `curl -i http://myserver:8096/health` 只用于说明语法，并非你的服务器，也不建议在公网传输凭据。若使用 HTTPS 或子路径，以实际部署和管理员规则为准，不绕过证书校验。记录状态码及时间，不公开完整响应头。

## 理解失败与未知

若取得 200，先记录状态码；由管理员确认响应确实来自该 Jellyfin 健康端点后，再记该时间和网络路径的检查成功，仍须继续检查账号与媒体。若超时、拒绝连接、404、403 或证书错误，应原样记录，不把所有现象统称服务器宕机。反向代理可能阻挡端点，路径也可能与示例不同。若正在启动或迁移，先咨询管理员并等待其确认服务就绪，不因一次失败反复重启或修改数据库。

## 在网页和云映分层验证

用获授权账号在浏览器登录管理员提供的 Jellyfin 网页，确认预期资料库与目标短片可见。然后在云映打开同一服务器和账户，检查是否显示同一资料库和片名；字段名称和入口以实际安装版本为准。若网页不可用而健康检查成功，记录为服务检查与网页访问结果不同，不推断具体原因。若网页可用但应用列表不可见，核对账号、网络和实际服务器身份。

## 观察同一片段

打开目标短片，分别记下是否起播、画面、声音及停止位置。播放失败时记录是打开前、起播时还是播放中发生；健康检查成功不证明文件路径或播放处理没有问题。若可复现，保持账号、网络和片段不变，按管理员建议记录时间后再复查一次，不连续改变服务器设置、视频格式与播放设备。不能完成的步骤填未执行，不补写预期结果。

## 用两次观察缩小范围

例如上午服务器刚启动时健康检查没有回应，十分钟后管理员确认启动完成并再次检查，记录为先无响应、后返回 200，并请管理员确认响应来源。然后网页可以登录，但云映仍未列出预期影片。这时可以确认的问题边界是服务状态、网页访问和客户端列表之间存在差别；两次检查间隔本身不能证明修复了什么。先比对管理员给出的服务地址、账户和网络，仍无法确定时将原始现象交给管理员。

反过来，如果网页和列表正常而视频在固定时间停止，可以记下该位置，并在获得授权后用网页播放器检查同一片段。相同位置失败是供排查的线索，不足以单独证明文件损坏；只有云映失败也不能单凭一次就断定应用存在缺陷。保留时间、片段身份及观察条件，避免把几次不同媒体的体验混成一次结果。

## 交接和恢复

将四行结果和实际错误阶段交给有权排查的管理员，说明网页与云映是否使用同一账号及网络。不要发送密码或完整私人链接；若日志中有访问令牌，先由管理员脱敏。检查结束后退出临时账号，确认原有服务、资料库和源文件保持原状。若管理员后来提供了新的诊断结论，单独补充确认时间和来源，不覆盖第一次未成功或未执行的原始记录。本教程基于公开文档，未声称已连接私人服务器或进行了真机测试。
