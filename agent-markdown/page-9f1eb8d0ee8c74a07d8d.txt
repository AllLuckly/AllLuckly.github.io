Use self-made non-sensitive comics to distinguish issue AgeRating, server aggregation and normal-account visibility.

## Understand aggregation

Kavita’s comic-metadata documentation says AgeRating can differ among files within a series and the series uses the most restrictive rating among them. A content classification is not a quality score and does not prove specific content. Server grouping, account restrictions and client display need separate checks; a visible series name does not prove the client exposes the full rating.

## Prepare non-sensitive isolated samples

Prepare two self-made, non-sensitive comic issues in an isolated library you administer and use a normal test account. Distinguish issues by visual markers and back up files and metadata; adult material is unnecessary. Fictional ratings test metadata handling and are not classifications of real content. If library and account settings cannot be restored, stop at read-only recording and do not alter real-user restrictions.

## Establish series and account baselines

In the server web interface record grouping, issue identity, visible issue and series ratings and the normal account’s library access. Administrators may bypass restrictions, so account outcomes must be observed as the normal test user. Find the series in Manyue+ using the same server and account and record issue count, displayed fields and actual entry points. Mark a missing rating field not displayed without assuming internal client behavior.

## Inspect each ComicInfo

In authorized copies, confirm ComicInfo.xml at each archive root and record Series, Number and AgeRating per archive. The documentation lists ratings from less to more restrictive; use only test values supported by the installed server version’s documentation. Do not combine fields from separate issues into one fictitious file or treat a blank as a specific rating. Mark unverifiable metadata unknown.

## Set a restorable control

Only after an administrator confirms isolation and restoration and an editor understands XML, set two different documented test ratings in the self-made copies, preserving original values. Keep series name and issue numbers stable and validate XML and archive structure. Do not simultaneously change account permissions or real comic ratings. If editing is unsafe, skip it and retain the baseline without claiming aggregation was verified.

## Check server recognition

Wait for or perform a test-library scan through the actual interface and record completion. Confirm both issues remain in the same series, then record server-recognized issue and series ratings separately. A series using the more restrictive test value is consistent with the documented rule. If not, check grouping, file fields, lock state and server version; matching names alone do not prove the new values were read.

## Check the normal user and client separately

As the normal test user, check series and issue visibility on the server, then inspect the same connection in Manyue+. If age or library restrictions apply, an absent series can be an access result rather than a client defect. Mark missing rating labels or entry points as not displayed. Do not substitute an administrator account or bypass existing restrictions.

## Do not treat metadata as content evidence

Ratings in this experiment are fictional test metadata and are not real classifications of the self-made imagery. Production classifications should come from reliable authorized sources and respect actual server settings. Do not label a work based solely on different field text. If a lawful sample or verifiable field is unavailable, record unknown and stop rather than downloading sensitive material.

## Restore and document

Restore isolated samples and settings from backup and confirm original files and other users’ data remain; defer uncertain effects to the administrator. Record per-issue fields, grouping, aggregated rating, normal-account and Manyue+ display and skipped steps. Remove private paths and credentials before sharing. This public-documentation guide claims no private-server or device test.

## Confirm the grouping precondition

The highest-rating rule concerns files the server actually recognizes as one series. Check Series, issue number, location and the server details page, then use self-made markers to identify both issues. If the second issue belongs to another series, its rating is not direct evidence for this series-level observation. Adjacent folders or similar names do not establish correct server grouping.

## Separate aggregation from account filtering

Server aggregation and a normal account’s permission to see the series are different questions. Have an authorized administrator confirm test metadata, then check visibility as the normal user, recording account and time at each step. If the series is absent, inspect that user’s library access and restrictions without changing others’ permissions. An empty client list alone does not establish aggregation failure.

## Record unknowns and restoration

If test values differ from official examples, check the installed version’s supported vocabulary instead of guessing rating order. Mark inaccessible samples, pending scans, locked fields and insufficient permissions distinctly as incomplete or unknown. Restore test files and settings and confirm prior account progress and other series remain. Remove internal paths and tokens before sharing.

## Reproducible test values

Reproducible sample: two archive-root ComicInfo.xml files both have Series River Demo, Numbers 1 and 2 respectively, and AgeRating PG and M. Both issues contain only self-made non-sensitive material; labels are test values. Confirm the installed Kavita version supports the values and groups both issues into one series, then scan and check whether its series rating uses the more restrictive M. Check normal-user visibility separately; do not assume the client displays the field.
