When customizing a 键来 theme, similar text and key-background colors can make labels hard to read. This exercise calculates contrast for two opaque sample pairs outside the app, then observes the actual keyboard if possible. W3C’s web contrast method is a reference for comparing colors, not automatic conformance certification of this native interface. Images, transparency, font, size and display conditions may alter the result.

## Prepare colors and a recoverable theme

Record the current theme and colors and confirm the actual way to restore them; do not overwrite the user’s valued configuration. Prepare an ordinary note with nonprivate `ABC 123`. If text or key-background colors are not adjustable in the current theme, complete the paper calculation and mark in-app setup not applicable. Do not assume there is a precise hexadecimal input.

Sample A uses white `#FFFFFF` text on medium gray `#777777`; sample B uses the same white text on darker gray `#595959`. Both are opaque flat colors without images, gradients or shadows. Only the background changes. These are not claimed app defaults. W3C has a 4.5:1 reference threshold for ordinary web text; here it compares the samples, not a claim of legal or comprehensive accessibility compliance for a native keyboard.

## Identify the two layers being compared

Choose a visible key label and the adjacent key background, not candidate text against the device wallpaper. If either is translucent, mark the flat-color calculation inapplicable until compositing is understood. A picture background can vary by position, so one configured color pair cannot establish readability of all keys.

Record text color, background color, opacity, source and intended interface for each pair. Candidate and body text are different areas needing their own comparisons. This exercise calculates one selected flat-color key label, not every candidate, icon or host document. Do not upload screenshots containing private input to an online checker.

## Calculate relative luminance

W3C’s method divides each 0–255 sRGB channel by 255 and linearizes it: divide by 12.92 at or below 0.04045; otherwise calculate `((s+0.055)/1.055)^2.4`. Relative luminance is `0.2126R + 0.7152G + 0.0722B`. White `#FFFFFF` has luminance 1. Each gray has equal channels, so one channel calculation suffices.

For `#777777` each channel is 119/255, producing about 0.184475 after linearization. For `#595959` it is 89/255, producing about 0.099899. Check with your own calculator; no image upload is required. Compare thresholds using unrounded intermediates. The displayed decimals only aid the calculation.

## Calculate contrast and explain the boundary

Use W3C’s formula `(L1+0.05)/(L2+0.05)` with the lighter and darker luminance. Sample A is about `1.05/(0.184475+0.05)=4.478:1`; sample B is about `1.05/(0.099899+0.05)=7.005:1`. Although A can be displayed as approximately 4.48, it is below 4.5 and must not be rounded into a pass. B is above 4.5. Contrast describes a color relationship, not every aspect of visual experience.

If using an external color tool, confirm the same sRGB method and opaque inputs, and record tool and inputs. Its label is not a report on the actual 键来 interface; actual observable theme colors require a separate check. Users can select what works for them rather than treating one number as proof that everyone can read it.

## Observe 键来 with a recoverable setup

Only if the installed version offers the relevant controls and the user wants to, apply colors close to the two examples in a recoverable theme copy or practice theme. Without a precise color entry, record the visible selection and do not claim exact `#777777` or `#595959` values. Do not apply flat-color results directly to a translucent or image background.

On the same device, brightness, host and layout, select 键来 and type `ABC 123`. Observe label, key boundary and candidate readability and correctness of body text separately. Readable key labels do not establish candidate or document readability. Change only one color condition and record actual results; changing font, size and image at once cannot isolate contrast.

## Troubleshoot and record limits

If the calculation and subjective readability differ, check the actual colors, transparency, background pattern and observed location. Antialiasing and font weight can affect edge appearance on screen. A paper formula does not establish every rendered pixel or every user’s experience. Do not ask users to stare at a screen for long periods or repeatedly dim it.

If the picker shows no values, actual foreground is unknown or an image covers the area, mark that condition unmeasured and keep a readable theme. Use self-made color blocks and nonprivate text for any support request. Check the original setting and save state before considering a reinstall or deleting theme data.

## Complete the record and restore

Deliver sample A and B colors and calculation, whether exact values could be set in the theme, key and candidate observations and committed text. Identify paper calculations versus actual device observations. Restore the original theme or keep the new choice as the user wishes and reopen an ordinary input area. Do not mark unperformed operations as passed. No keyboard device, vision or accessibility-conformance test is claimed.
