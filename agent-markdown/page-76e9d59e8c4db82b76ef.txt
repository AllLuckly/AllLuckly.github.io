The same keyboard may look different in ordinary text, email and URL fields because a web page gives the system an input-type hint. Whether the host, system and third-party keyboard use that hint must be observed. This exercise compares the visible 键来 layout and committed text in a local HTML sample that sends no data. It does not assume a particular key layout.

## Prepare a non-networked practice file

Use an existing plain-text editor to create a UTF-8 file named `fields.html` with the complete sample below. It has no submit button, script, remote asset or network address and requires no account. Three labeled fields use `example.com`, a reserved example domain, as text only; do not send mail or navigate to it. Do not enter a real email, password or work address.

```
<!doctype html>
<html lang="zh-CN">
<meta charset="utf-8">
<meta name="viewport" content="width=device-width, initial-scale=1">
<title>输入框练习</title>
<label>普通文字 <input type="text" autocomplete="off"></label><br>
<label>邮箱 <input type="email" autocomplete="off"></label><br>
<label>网址 <input type="url" autocomplete="off"></label>
</html>
```

HTML defines different input states, but a field type does not guarantee a specific keyboard key or establish that entered content has been validated. There is no form submission, security assessment or email sending here. Confirm the suffix is not `.html.txt`. If the device cannot open a local file as an interactive page, use an offline test environment you control or mark it pending. Do not upload it to an unknown site.

## Define samples and an observation table

Prepare three nonidentifying strings on paper: `tea` in the text field, `a@example.com` in email, and `https://example.com/` in URL. Record host and OS, active keyboard, field type, visible keys, committed result and pending items for each. Keep separate rows to avoid conflating focus and keyboard changes.

Display all three labels in a browser or known-safe preview that supports this local page. Confirm fields can be focused, no submit action exists and no unknown site is contacted. If preview is not interactive, shows plain source or the environment is unclear, stop. Do not replace the local exercise with real data on a public test site.

## Establish the ordinary-field baseline

Focus the text field, select 键来 using the system keyboard switch, and confirm the keyboard actually shown. Enter `tea`, check all three lowercase letters in the first field, and record whether letters, a symbols entry and a return-key label are visible. This result applies to this host and keyboard. A candidate is not necessarily committed to the field.

If the third-party keyboard does not appear, first inspect the system keyboard list, focus and whether the browser permits that input method. The system may use another keyboard in certain fields or situations. Do not disable security or delete installed keyboards. Mark the baseline incomplete rather than attributing a system keyboard’s appearance to 键来.

## Check the email field

Focus the email field and observe whether 键来 is still selected, whether `@` is visible, whether another key surface is needed and what the return key says. Record the actual display, not a predicted one. Enter fictional `a@example.com` and verify lowercase letters, one @, one dot and the domain. Do not click a link or send email. A browser format hint does not prove the address exists or receives mail.

Record a system keyboard switch, or an ordinary 键来 layout that can enter @ through symbols, as observed. An HTML email field can influence a host’s keyboard hint, but actual layout depends on the system and input method. Lack of a special email layout does not mean the content cannot be entered. For failure, check focus and selected keyboard before recording; field type alone does not establish an app defect.

## Check the URL field

Focus the URL field. Record the active keyboard, how slash and colon are entered, and the visible return label. Enter `https://example.com/` and check the colon after the scheme, two slashes, domain dot and final slash. Do not navigate or test a real site; treat the string as text. If the host changes case or punctuation, record before and after without attributing it automatically to 键来.

Before comparing with email, confirm the same keyboard and orientation were used. Changing field together with theme, OS or browser makes the comparison hard to interpret. Record another browser as a separate round. Even with identical layouts, check the actual text in each field because the required characters differ.

## Troubleshoot and protect existing settings

If a character is missing, inspect layout and the actual symbols entry first. If text differs, check uncommitted candidates, automatic replacement and whether focus is in another field. If the local page does not open, check file suffix and editor encoding; do not disable browser protection or grant extra permission. Change one understood condition per retry and preserve actual errors rather than erasing the history.

For a system keyboard comparison, record that the keyboard changed. A dedicated layout in one keyboard does not establish that 键来 must match it. In either case, a browser validity hint is not validation of a real account. For support you may provide the nonprivate HTML, versions and visible feedback without private input or identifying screenshots.

## Save observations and finish

Deliver the three-row table and local test file with field type, keyboard identity, how required characters were entered, final text and untested items. The user decides whether to clear fields or delete the sample. Restore the everyday keyboard and display settings.
