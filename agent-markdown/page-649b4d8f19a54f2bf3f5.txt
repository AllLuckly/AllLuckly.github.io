{% raw %}# ManYue CBZ compression methods: listing an archive does not prove every image can be read

Record compression methods and read results per image, separating container recognition, external decompression and ManYue display.

English translation of the [Chinese original](<https://allluckly.cn/guides/manyue-cbz-per-entry-compression-method/>), translated on 2026-11-10. Original publication dates, attribution, code and version notes are retained.

A CBZ may list successfully yet fail at one image; page order is not the only possible cause. Check each ZIP entry’s compression method and compare it with actual ManYue display. This differs from an archive integrity check or suffix change. A method permitted by ZIP is not necessarily supported by the installed app, and external-tool results need their own record.

## Choose a small owned sample and retain the original

Choose a permitted three-page archive you made or obtained from a trusted source. Retain the original and a separate working copy. Record its complete name, source, byte size, app version and the version of an already available desktop archive tool. Give the three images distinct A, B, C corner marks and retain their unpackaged originals. Do not fetch an unfamiliar archive or process a whole library to investigate one method. If the working copy is still a cloud placeholder, confirm the actual file is available first; a shelf cover does not establish that every image’s data is local.

## Record methods per entry, not only the archive label

In an already trusted tool’s archive details, inspect each image’s full path, entry index, compression method, compressed/uncompressed sizes and visible errors. ZIP entries may use different methods; a ZIP label at the top does not answer for every item. If Python is already installed, its zipfile entry information permits knowledgeable users to inspect metadata read-only, but this is external to ManYue and does not require installing software. If the tool does not expose the method, record that limitation instead of guessing from size. Mark directories and explanatory files separately rather than counting them as displayable images.

## Distinguish compression identifiers from image encoding

An illustrative list might assign method 0 to A, 8 to B and 12 to C: stored without ZIP compression, Deflate and BZIP2 respectively. This is a hypothetical list, not an app test report. The image itself may still be JPEG or PNG; archive compression and image encoding are separate layers. Method 0 does not mean an image escaped JPEG compression, only that the ZIP layer does not compress that entry again. Retain both image type and archive method. PNG support does not establish support for every ZIP method containing PNG data, and a larger identifier is not a quality rating.

## Check entry listing separately from content reading

For the known small sample, open or save A, B, C individually to an empty working directory only if the existing tool can select an individual entry unambiguously. Record successes and exact errors. Do not extract everything over a production directory or proceed with an unknown enormous expanded size. Listing proves directory metadata was read, not that members can be decompressed. Unsupported methods, corruption and invalid images remain different possibilities. If the external tool extracts C, that establishes only this tool’s current result for that member, not ManYue compatibility. Preserve the original error wording.

## Check every corner mark and neighbouring page in ManYue

Import the working copy and open it through the actual available control. Find A, B, C corner marks and record chapter, app position, result after waiting and neighbouring images. Instead of “page three is broken,” map the expected mark to its archive path and method. If display order differs, match marks rather than equating directory indices with app page numbers. When external reading works but app display does not, image encoding, dimensions and completeness still need consideration; method is only a candidate cause. Do not invent a compression-compatibility menu if the app exposes no such technical detail.

## Repackage only from confirmed originals when needed

If a compatibility control is needed, use only the three originals already confirmed readable. With an existing trusted archive tool, save a separate ZIP reading copy using one documented common method and name it under the CBZ convention. Record the actual option; do not promise it works in every app version. Repackaging changes container bytes, so the new fingerprint cannot prove identity with the original archive. Retain image-path order and the old/new mapping rather than deleting unknown members to obtain success. Renaming a ZIP suffix does not change internal compression, while image transcoding would introduce another variable.

## Change only the archive layer and retain uncertainty

Import the original working copy and uniform-method copy separately. Compare every mark, image dimension and dialogue passage, recording whether the result changes with the archive layer. If images are also resized, renamed and recoded, an improvement cannot be attributed solely to compression. If both fail, return to image and source checks; if both succeed, that does not establish compatibility for all archives using those methods. When the original member was not reliably readable, mark its content unresolved rather than using a newly downloaded edition as an identical-content control. Share an owned small sample and per-entry list, replacing private paths with structurally faithful example names.

## Exit and return to complete the three-layer result record

Exit the reader and return to the two clearly named copies. Relocate A, B, C and the neighbours of any failure, checking that the correct edition is open. Keep original path, image type, ZIP method, external reading result, app display and modification scope on every row. Separate integrity-check success, decompression success and complete reading; one success icon cannot replace all three. Completion means a particular entry’s failing layer can be reviewed, not that every CBZ can be repaired losslessly. Unsupported-method explanations remain provisional unless evidenced, rather than becoming an invented official compatibility list.
