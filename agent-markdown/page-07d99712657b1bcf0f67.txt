A large private comic and failure screenshot may not let someone repeat an import issue. Build an original shareable three-page sample and instructions, then check whether it actually reproduces the issue. This is not first-import setup or a promise that simplification preserves every defect, and manual preparation is not automatic app diagnosis.

## Record the original issue before sharing files

Privately record app/system versions, format, size, entry, destination, expectation and actual message, identifying selection, processing or reading stage. Do not invent an error. Retain the original without sending the whole work anywhere. For private-server issues, record connection type and permissions, excluding credentials from the shareable draft. Separate necessary conditions from incidental background instead of including unrelated titles, accounts and complete device logs.

## Create three unambiguous original pages

Make three pages in a familiar existing tool, each with number one/two/three and a different phrase, identifying a self-made test on page one. Use original simple graphics, numbered filenames and recorded dimensions, format and packaging tool, retaining sources. For a large-image issue, preserve relevant dimensions only with adequate resources, without stuffing unknown files or exhausting storage. Three pages reduce content, not necessarily every parameter. State simplifications rather than calling it a lossless miniature of the original.

## Change one relevant condition at a time

Confirm a baseline with three externally readable pages, then change one condition directly relevant to the original issue, such as directory depth or dimensions, in a separate control. Do not change extension, colour, path and compression together. Name baseline A/control B and list differences, all using your material. Without a suspected condition, retain not isolated instead of randomly damaging files to obtain a different error. Narrowing scope need not produce failure; successful results matter too.

## Actually repeat the same entry path

Process baseline and control through the recorded entry, noting file, time, processing state and result. After success, open all three pages, check phrase order, leave and return rather than relying on a shelf cover. If the sample does not reproduce the original issue, say so with remaining differences; do not pair success screenshots with a failure claim. For entry-specific behaviour, record both paths instead of generalizing one server or picker path to all imports.

## Write the shortest repeatable instructions

Include six items: prerequisites, sample, entry, actions, expectation and actual result, numbering only real actions. Separate observation from hypothesis: page three blank differs from possible decoding issue. Retain necessary screenshot context without cropping relevant edges or error wording. Do not promise failure within ten seconds without evidence; record observed duration and whether processing completed. A reader should understand the goal and stopping point without the library’s whole history.

## Check shareability and sensitive data

Open every deliverable and verify original pages and metadata, names and screenshots free of private paths, accounts, tokens or others’ works. Keep only relevant log fragments, with originals private. If sanitization changes reproduction conditions, rerun and describe it instead of attributing an old result to a new sample. Preparation sends nothing automatically; sharing uses your chosen authorized channel. For login-dependent behaviour, supply conditions rather than packaging passwords for convenience.

## State dependencies and limits clearly

Repeat from instructions without supplying hidden steps from memory, using a clean local copy where feasible without reinstalling or clearing a real library. State network, permission or large-file dependencies absent from the offline sample. CRC covers its test layer, not universal content safety, and external display does not prove every parameter supported in ManYue. Classify reproduced, unreproduced or partially reproduced honestly, retaining unexpected results rather than polishing them away.

## Preserve a versioned package after returning

Finally leave the reader and return, confirming the three pages, order and state referenced in the instructions. Preserve package version, instruction date and file inventory. Recheck and version any later file change instead of reusing old screenshots and results. Keep original issue material separately, outside the shareable package. Completion identifies files, actions/results, dependencies and untested scope so others can judge repeatability, not proof of repair or guaranteed resolution from one report.
