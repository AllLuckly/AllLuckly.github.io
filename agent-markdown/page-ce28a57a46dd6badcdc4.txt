Use a self-made CBZ to check file identity, transfer integrity and reading, distinguishing archive errors from image errors.

## Preserve the original and record the failing copy

Choose a self-made CBZ you may use, retain the known-readable original safely, and put the failing copy in a working folder. Record names, byte sizes, acquisition method and time without uploading private comics to public reports. If only one irreplaceable original exists, back it up first. Later checks must not overwrite or attempt repair on the only original.

## Identify which copy was imported

Record different names and locations for the original and failing copy, then import the failing copy through an entry actually visible in ManYue. Distinguish inability to select, transfer failure, import failure and failure after import. A shelf cover does not prove every page is readable. If the app identifies both copies as one item and their source cannot be confirmed, mark identity pending rather than deleting other works to force recreation.

## Inspect both files with an external tool

On a computer use a trusted archive tool to see whether both copies list their members. CBZ commonly uses a ZIP container, and renaming an extension does not repair damaged content. Record image count, paths, messages and whether entries can be read. A successfully listed directory does not prove every image payload is complete. Do not execute programs from unknown archives or upload private files to untrusted sites.

## Compare file sizes and checksums

Using a familiar local tool, calculate the same hash algorithm for each copy and record algorithm, file identity and result. Matching hashes provide strong evidence of identical bytes; a mismatch establishes different bytes but does not alone tell you which part is damaged or whether contents are readable. Equal file sizes do not prove identical content. Hash the copy actually imported, not merely another file with the same name.

## Check the container and individual images separately

Python’s official zipfile documentation describes checking ZIP members and their data. Use a trusted local tool’s documented read-only integrity test on the working copy and record pass, failing member or inability to test. A container check does not guarantee that ManYue supports every image format or displays the intended page order. If a particular image is reported, inspect it in a safe working copy with an image viewer without executing unknown content.

## Compare the original with a newly transferred copy

If the original reads completely and the failing copy differs in hash or container result, transfer a fresh copy from the original to a clearly named new location. Keep both the original and first failing sample. Record transfer completion feedback, target size and hash, then import the new copy and inspect the same chapter. If bytes match but app behavior differs, record device, source and actual messages without automatically blaming transfer.

## Distinguish three files with a redacted ledger

Label the original A, first failing copy B and retransferred working copy C. Privately record actual location, byte size, hash using the same algorithm and read result. If A and B differ while A and C match, then check whether the external archive tool can read C member by member. This supports byte identity between C and the original, not the exact point at which the first transfer failed. If A and B match and both pass a container check but only one import fails, confirm the same file and entry were used before recording app feedback; a checksum is not an app-compatibility guarantee. Mark any uncomputed hash untested rather than substituting file size.

## Keep a minimal diagnostic sample for a bad image

If a tool explicitly identifies an image member, record its relative path and original message, then check whether that same member opens in A. Only for self-made material you may handle, consider a separate minimal working package containing the neighboring pages and that image to narrow the comparison; after replacing content, do not call it the original failing archive. If the issue appears only in the original archive, record changed conditions such as compression tool or directory depth without claiming a single cause. Before sharing with support, check that the sample contains no private or restricted third-party material; otherwise share only redacted steps and error type.

## Finally check file locations

After documenting feedback, return to the original archive’s location to check its name and size, and verify that the safe backup still opens. If a tool offered to modify or overwrite and the user cannot confirm what happened, retain the message and mark the original’s state pending. Clean up only positively identified test copies you created; do not bulk-delete based on matching names.

## Verify pages and deliver diagnostic records

In a copy that actually opens, inspect the first page, last page and page where the failure occurred, identifying them by visible text or marks rather than page count alone. Record original and copy labels, sizes, hash algorithm, archive checks and app feedback; mark unperformed repairs or device tests untested. Preserve the original comic and backup, cleaning up only your own test copies if desired. No real import, integrity check or device test is claimed.
