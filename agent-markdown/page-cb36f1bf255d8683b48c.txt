## Prepare identifiable test content

On your own Jellyfin server choose a library available for testing and a nonprivate short video, recording library name, video title, duration and opening. Prepare two test accounts A and B that you are authorized to use. Do not use another person’s account or change permissions on a shared server without permission. Preserve original media and production accounts; stop if authorization is unclear.

## Record existing user permissions first

Jellyfin’s user-management documentation describes per-user library access. An administrator checks A and B’s actual permissions for the test library in the current server interface and records original states; no permission change is needed for practice. Use account names locally only and A and B in shared records. If permissions cannot be inspected, mark unknown; a missing client library alone does not prove access was denied.

## Compare the same library on the server side

Sign in to a Jellyfin client or web interface as A and B in turn. For each account check whether the test library and video appear and, where authorized, play the opening. Sign-in, library listing, video listing and playback are different layers; successful sign-in does not grant every library. Confirm the actual signed-in account each time so a retained browser session does not attribute A’s result to B.

## Confirm the account used by iCouldPlay

Open the existing Jellyfin source in iCouldPlay and confirm server identity and current account using the actual interface. Switch test accounts only if connection information can be preserved safely and the comparison is needed. Record each account’s visible libraries and videos in iCouldPlay and play the authorized test video. Public information supports Jellyfin but does not promise identical user-configuration interfaces; if account identity is unavailable, mark unconfirmed rather than guessing.

## Compare server and client outcomes

If A sees the library in both Jellyfin web and iCouldPlay while B sees it in neither, the administrator can inspect B’s actual permissions. If B sees it on the web but not in iCouldPlay, first confirm the same account, server, network and library, then record versions and observations. Do not grant all-library access solely because the client lacks an entry or use an administrator’s result as proof of a restricted user’s access.

## Preserve permissions and record results

If an administrator must change access, record the original state, make only the necessary approved change to the test library, sign in again and check that account’s visible scope, then restore as agreed. Record test time, redacted account identifiers, whether original access was confirmed, library and playback results on both sides, and untested items. Do not share passwords, tokens or private media. This article follows public documentation and claims no device or server tests.

## Avoid account confusion with a ledger

Use rows A and B and columns for confirmed server access, visible Jellyfin library, visible video, opening playback, visible iCouldPlay library and iCouldPlay playback. For example, if A has observations in all columns while B’s access is unconfirmed and the library is absent, record B’s access as unknown and library as not observed—not denied. After switching accounts, verify identity in the actual interface before acting. If the account is not displayed, stop that comparison and retain the connection settings.

Suppose an administrator confirms B can access the test library and B can play it in Jellyfin web, but iCouldPlay does not show the library. First confirm the same server, B account and source in iCouldPlay and allow the current interface to finish loading. If the difference remains, send redacted results to app support. Web playback and an absent client entry are separate facts; neither proves that all server settings are correct nor immediately identifies a client defect.

## Distinguish library access from one playable video

If a user sees the library but cannot play one video, compare another small authorized video from that same library under the same account and record both results. If only one fails, inspect whether that file is readable on the server and what the server actually reports; do not attribute every failure to account access. Conversely, if the library itself is absent, inspect account and library access first rather than guessing a video codec.

Accounts may have other server-side restrictions; include a restriction in the record only if an administrator can verify it. Do not widen access to other libraries or disable account protection as a quick test. If a change is needed, establish its scope, original state and restoration owner; change one condition and retest the same video. If no permission was changed, record “unchanged” rather than describing a read-only inspection as a completed fix.

## Consider cached displays and signing in again

After permissions change, an already open page may retain an earlier display. Exit and reopen the source using the current client interface, and record when you signed in again and the server authorization state. Do not assume a fixed refresh interval. If you cannot safely sign out or identify the account, stop the comparison rather than overwriting an existing connection. An old listing alone does not establish continued access; check actual directory and playback under the account’s authorized scope.

After testing, compare A and B’s server permissions with the pretest record. If the administrator intentionally retains a change, the administrator should document the new scope. Exclude account names, full addresses and reusable links from shared reports; use A, B and a test-library identifier.
