> "Our company project recently needed Lianlian Pay integration. The documentation was unclear and we encountered several pitfalls, so I recorded them in the hope of helping others."

The basic integration did not cause problems. Here I organise the official integration documentation into the following steps.

> Import files

> Add the header-file reference.

> Set Target → Build Setting → Other Linker Flags to -all\_load. If -all\_load conflicts with another library, try -force\_load to load one library. Follow force\_load with the full path to the lib file: -force\_load $(SRCROOT)/***/libPaySdkColor.a (***\*Choose this according to the path where your library is stored.)

> Call the SDK to display it. Retain it: calling it after autorelease causes a crash.

```
self.sdk = [[[LLPaySdk alloc] init] autorealse]; // 创建
self.sdk.sdkDelegate = self;  // 设置回调
NSDictionary* signedDic = [payUtil signedOrderDic:orderParam andSignKey:md5key_or_rsakey] // 加过签名的订单字典
[self.sdk presentPaySdkInViewController:rootVC withTraderInfo:signedDic];
```

> Write the result callback.

```
// 订单支付结果返回，主要是异常和成功的不同状态
- (void)paymentEnd:(LLWalletPayResult)resultCode withResultDic:(NSDictionary *)dic
```

### Configurable SDK components

The iOS SDK can be customised through its resource bundle. Because the resources are inside the bundle, clean the project after modifying them for the changes to take effect.

> 1. Replace the internal images with your own designs.

> 2. Modify colours in default.css. Both #abcdef and 123,123,123 notation are supported.

> 3. List of configurable values and their meanings

Navigation-bar colour: replace shoushi3.png and modify background-color under NavBar in the CSS file. All field names below refer to default.css. Navigation-bar title: titleIconName and titleText under NavBar.

### Parameter fields

The demo contains parameter descriptions. Field names differ from WAP, so consult those descriptions. user\_id is not the merchant number; it is the user identifier in the merchant’s own system. For card-number-first input, no\_agree is the linked-card sequence number obtained through the API.

## Usage

The demo’s input fields test different payment conditions, including authenticated payment with name and ID number, and card-first payment with card and agreement numbers. They are not mandatory; test according to your payment method. The number of supported banks depends on payment type and merchant configuration. Contact operations to configure it. Payment verification methods—SMS, gesture code or payment password—must be configured by our server staff. Contact the relevant server-integration staff.

### Frequently asked questions

Prefer generating signatures on the server. If signing on the client, use payutil from the demo.

> 1. The app crashes immediately when run.

Answer: the SDK was not retained.

> 2. The SDK uses class extensions; add -all\_load to Other Linker Flags.

> 3. An initialisation error is reported.

Answer: 1. Check that the environment and merchant number match. 2. Check the signing method against the signature tool. 3. Check for omitted order information.

> 4. Common initialisation errors, explanations and responses

1. The supplied type is not NSString.  
 Explanation: Lianlian orders require values in the form {“strkey”: “strvalue”, “strkey1″ : “strvalue2“}. Do not pass {“key”: \[v1, v2\]} or {“key”: {“ikey”:”v”}}. Response: change the order-value format, especially risk\_item, to a form such as {“risk\_item”:”{\\”r\_key\\”:\\”v\\”}”}.

2. The merchant does not have permission for this payment product.

Explanation: our products include authenticated payment, quick payment and other methods. Each method has a different package, payment call and merchant number.  
 Response: first check that the merchant number is correct, for example \<authenticated-payment test merchant number 201408071000001543\> and \<quick-payment test merchant number 201408071000001546\>.   
 Then check the corresponding package and call method. Dedicated methods have already been extracted for iOS.

```
// 快捷支付
- (void)presentQuickPaySdkInViewController:(UIViewController*)viewController withTraderInfo:(NSDictionary*)traderInfo;
// 认证支付
- (void)presentVerifyPaySdkInViewController:(UIViewController*)viewController withTraderInfo:(NSDictionary*)traderInfo;
```

3. The merchant does not have permission for this payment method.  
 Explanation: each merchant number supports a limited set of product business types.  
 Response: change the merchant business type. busi\_partner is String(6). Virtual-goods sales: 101001.  
 Physical-goods sales: 109001  
 External-account top-up: 108001

4. Signature verification fails.  
 Explanation: signing follows specific rules and includes specific order parameters.  
 Response: the latest iOS demo provides payUtil, which directly generates an order with a valid signature. Again, we strongly recommend that merchants sign on the server.

### After payment succeeds, no extra handling is required here; the backend has submitted through the callback URL. During integration, notify\_url in the dictionary must be the server callback URL supplied by the backend staff integrating Lianlian Pay.
