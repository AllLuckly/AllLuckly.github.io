Transfer two small self-made comics first, then record individual and batch sizes in consistent units.

## Prepare two small original samples

Make two short CBZ archives you may use, for example A with two pages and B with three visibly numbered pages. Keep the original images and archives. Use files small enough to validate the workflow; there is no need to create a near-limit file. Record actual byte sizes, names and sources, then open each on the computer to rule out empty or damaged samples.

## Understand the published limit’s scope

The public 2.0.5 update notes say the Wi-Fi single-file limit increased to 2 GB. This describes one Wi-Fi file, not a universal limit for all sources, a batch total, bandwidth or available device storage. Installed-version behavior and actual messages govern. GB labels may also differ from binary unit displays, so do not decide a borderline file’s eligibility from a rounded label alone.

## Make an individual-versus-total table

Make three rows for A size, B size and the sum A+B in bytes. For illustration, 1,200,000 bytes plus 800,000 bytes equals 2,000,000 bytes. These are arithmetic examples, not actual file sizes or server capacity. Compare each file condition first, then discuss the total. Each item meeting one condition does not guarantee that the batch succeeds.

## Confirm the current Wi-Fi session

Open the Wi-Fi import entry actually visible in the installed app and visit the address displayed for this session from a computer on the same trusted local network. Check network permission and session identity. Do not publish private addresses, tokens or QR codes. If the page cannot open, follow the existing connection troubleshooting guide first; inaccessibility is not itself evidence of a file-size limit.

## Upload two small files individually first

Upload A once and record actual browser and app feedback. Identify the sample on the shelf and open its first and last pages. Then upload B in the same way and check its three pages. Record transfer, import and reading separately; a full browser progress bar is not proof that the app completed import. If same-named entries merge or cannot be distinguished, record identity as unconfirmed instead of deleting other comics.

## Check a batch only if actually available

If the current page really offers multiple-file selection, choose working copies of A and B for one batch and record total bytes and each item’s success or failure feedback. If multiple selection is unavailable, mark it unavailable rather than inventing a batch control. Even when two items are submitted, check shelf entries and content individually. On one failure retain its original message and file rather than repeatedly sending the entire batch.

## Troubleshoot a large file in layers

For a larger comic you actually need to import, first read its actual byte count and the app’s current message, then check computer and device space, archive integrity and network state. Small-sample success does not guarantee large-file success, and being under a limit does not guarantee every compression format is readable. If the interface does not specify the exact byte threshold or cause, mark it unknown instead of treating low storage, interruption and corruption as the same limit error.

## Do not mix decimal and binary labels

For size estimates, start with a byte count the system actually displays. By decimal definition 1 GB is 1,000,000,000 bytes; by binary definition 1 GiB is 1,073,741,824 bytes. Thus 2 GB and 2 GiB are not equal in bytes. This is only a unit conversion: it does not establish which threshold the app’s “2 GB” uses or guarantee acceptance of a borderline value. Compare small samples in bytes; if the system shows only rounded values, mark precision insufficient and inspect details or a trusted tool. Do not conflate disk allocation, compressed-file bytes and extracted content size.

## Record each batch step instead of only the total

In the results table give A and B separate columns for submission state, browser feedback, ManYue import feedback and opening first and last pages. If the browser reports both finished while A opens and B is still processing, retain A’s present result separately from B’s pending state; completed total bytes do not establish B’s success. If one item fails, verify its name, size and upload destination against the source before deciding whether to retry only that item. Record locking, network changes or browser closure only if they actually occurred during transfer. Stop retrying when items cannot be distinguished, to avoid ambiguous same-name copies.

## Keep original measurements in consistent units

Keep both the system’s displayed label and actual byte count in the final table, with source and observation time, marking either unknown if unavailable. A file still being copied may not yet have a stable size. Wait for actual completion feedback before recording it; do not treat a mid-transfer value as the final size or app limit.

## Preserve samples and organize results

Keep redacted device and app versions, A/B byte counts, action method, per-file transfer and reading outcomes, and whether a batch was actually tested. Close the session you opened and confirm original comics and images remain. Do not attach private addresses or someone else’s full comic to feedback. The exercise uses public release notes and local size checks and does not claim uploads or threshold tests.
