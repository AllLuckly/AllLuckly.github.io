## Prepare one text prefix and a separate drawing

Use an owned still-scene clip at least fourteen seconds long, preserving normal subtitles/video. Each event starts with BASE and one space, enters p1 drawing for an 80-wide, 30-high rectangle, then returns to text mode with p0. Text is a relative reference within the event, not a promise of a device-measurable font baseline. Fix a 640 × 360 script, example Arial size 36, both scales 100 and zero border/shadow. Record fallback and hold font, size and video fitting fixed rather than manufacture the expected position through altered line layout.

## Assign separate intervals to zero and signed offsets

Use pbo0 at 1–4 s, pbo20 at 5–8 s and pbo-20 at 9–12 s, with identical text, path, position (120,140) and remaining parameters. Observe inside events, for example at 2, 6 and 10 s, rather than only a transition frame. These are successive static conditions without interpolation; their gaps are not continuous translation animation. Ask separately about drawing direction relative to baseline, rectangle dimensions and line-position conditions. The sign belongs to the drawing offset, not event timing: the negative-offset event still starts at 9 s, not twenty seconds earlier.

## Read the documented downward and upward directions

Aegisub defines pbo as a drawing-baseline Y offset: positive places the drawing below the baseline and negative above. Calling pbo20 an upward shift reverses the definition. It neither resets pos nor changes video-frame coordinates. Interpret the script’s downward Y direction at a fixed drawing scale. Font metrics, line bounds and alignment anchors can affect final layout, so adding 20 to pos Y 140 does not establish a rectangle top at device pixel 160. Absolute bounds need separate rendering/measurement evidence.

## Check local ranges at fixed p1 without claiming device pixels

The external paper model covers only this p1 drawing at vertical scale 100, mapping local y to y plus the offset. Its original x range is 0–80 and y range 0–30; offset 20 gives y 20–50 and offset -20 gives -20–10. Width 80, height 30 and area 2400 remain unchanged; negative coordinates do not create negative height. Check corners too: positive twenty takes upper-left (0,0) to (0,20) and lower-right (80,30) to (80,50). Both move equally, not just the bottom edge. Negative twenty gives (0,-20) and (80,10); the lower endpoint 10 is not a new height of 10. This distinguishes translation from a height parameter, without calculating font line boxes, player overrides or device pixels. Different drawing modes/vertical scales need separate models rather than this fixed-condition table.

```
Declared LOCAL p1 model; fscy=100; NOT device pixels
pbo 0:   x [0,80], y [0,30],    width 80, height 30, area 2400
pbo 20:  x [0,80], y [20,50],   width 80, height 30, area 2400
pbo -20: x [0,80], y [-20,10],  width 80, height 30, area 2400
pbo 10:  x [0,80], y [10,40],   width 80, height 30, area 2400
```

## Change only positive twenty to ten for a control

Save drawing-baseline-ten.ass and change only event two from pbo20 to pbo10, preserving timing/path literally. Its paper y range changes from 20–50 to 10–40, with unchanged width, height and area; it neither returns to zero nor halves height. Compare only original/modified second events after re-association, preserving the original and negative event. Changing pos involves prefix/line positioning and is another task. Replacing path coordinate 30 with 15 changes path height; that mixed modification cannot demonstrate pbo scaling.
