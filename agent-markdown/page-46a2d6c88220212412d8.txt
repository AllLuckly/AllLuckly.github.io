Record the reading states of two existing connections for one authorized test book, then verify results against actual merge prompts.

## Confirm version and action scope

In Apple lookup samples, some China responses still showed 1.1.4, while cache-varied China, Finland and US responses showed 1.1.5, whose public notes mention merging reading progress from existing connections. Actual store and installed versions can differ. Record the device and version and confirm the entry exists. This exercise does not assume every server type supports merging or equate file copying with merging progress.

## Preserve both existing connection states

Label the old connections A and B and record each service type, redacted address label, account and root-directory identity. Do not retain passwords or tokens or publish real hosts. Confirm that recoverable backups of existing data are available and understand how to preserve them. Without backups or a clear action scope, perform read-only comparison only; do not delete a connection or confirm a merge.

## Confirm the same library and edition on both sides

In the authorized server-side views for A and B, inspect directory structure and the same EPUB you may read. Record title, chapter, file source and a distinctive sentence. Matching names or covers do not prove the same edition. If possible, compare checksums of originals you own as separate byte-identity evidence; different bytes do not automatically imply different text. Stop while identity remains uncertain.

## Record reading positions in both sources

Without changing connection configurations or sync direction, switch to A and B in turn, open the sample on each, and note the chapter, identifiable sentence and observation time for each. Opening can itself update reading state, so prepare the baseline first and record actual changes. Do not decide which point is later from percentages alone: covers, contents pages and layout can affect them. Mark a side unobserved if it cannot be opened.

## Identify the actual merge entry and prompt

Find the installed version’s actual entry for merging existing connection progress and read what it says about source, target, time, conflicts and outcome. Do not guess from names if only one connection is listed or the target is unclear. If the interface does not specify a scope, do not promise notes, bookmarks or files are included. Record nonsensitive prompt details; no merge has yet been performed.

## Record a conflict with observable anchors

For a nonprivate test book record chapter name, contiguous short phrase, observation time and visible interface state separately for A and B. If A is in chapter one and B is in chapter two, a larger percentage or later time alone does not determine which is more important; the user may want to preserve a note on A rather than B’s position. If the interface promises only progress merging, do not claim notes or bookmarks are guaranteed. Before performing a merge, identify the intended outcome, whether the user can recover from backup and whether the prompt explains conflicts. If any is unknown, retain both states and complete only the observation table and retain the original record.

## Assess conflicts and recoverability

Compare A and B’s chapter anchors and observation times and identify what the user wants retained. A newer timestamp does not necessarily mean a more complete record. Check conflict handling in the prompt and whether backups can actually be restored. Stop if retention rules, target or recovery remain unclear. Do not simulate merging by repeated uploads, downloads or account changes. A read-only check remains unperformed.

## Perform one merge only when conditions are clear

Only when sources and target are identified, recoverable backups exist and the user understands the prompt should you perform one merge through the actual interface. Record connection labels, start time and visible result without credentials. On failure or interruption preserve the message, stop repeated taps and check the backup and actual outcome. A completion button or message is feedback, not proof that every record merged correctly.

## Keep completion messages and verification in separate rows

Use three rows for interface message, target-book opening result, and original connection and backup state. Even when the first reports success, fill the second only after actually opening the target sample and locating its anchor. If no merge was executed, mark the rows unperformed or untested. Preserve incomplete results rather than repeatedly confirming a merge to force a conclusion.

## Wait for clear evidence before continuing

If the interface gives only a generic success message, retain original connections and backups and mark bookmarks, notes and other books outside the explicit scope pending. For support use only a self-made sample, redacted connection labels and actual prompts; never attach server secrets, private domains, accounts or the complete private library.

## Verify the sample and record unresolved items

If a merge was performed, reopen the same edition on the target connection and compare chapter and sentence with the earlier A/B records. Check important bookmarks or notes separately and state whether the interface included them in its promised scope. If results differ, preserve current data and errors while determining a recovery plan. Keep redacted A/B identities, prompt, execution state, observations and untested items. No physical-device or private-server operation is claimed.
