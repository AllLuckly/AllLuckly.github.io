Use self-made comics to compare ComicInfo Count, publication status and completeness in your own library.

## Understand the documented rule

Kavita’s comic-metadata documentation says that when the field is not locked, a defined nonzero Count in at least one ComicInfo can cause the publication status to be treated as ended; when Count matches the volume or chapter count, the series can be treated as completed, meaning all items are owned locally. Ended publication, collection completeness and personal reading completion are distinct conclusions.

## Prepare an isolated sample

Use an isolated library you administer and two short self-made comics, preserving original files and metadata backups. Distinguish the two issues with visible self-made markers and use a normal account authorized for the library. No real purchase or other person’s media is needed. If restoration or editing authorization is unavailable, observe read-only and do not change production files or reading progress.

## Record series and current state

Find the test series in Kavita’s web interface and record title, visible issue or volume count, publication status, ownership status and user reading progress, marking absent items not displayed. Check for same-name series or locked fields. Find the same item in Manyue+ using the normal account and record fields and chapters actually visible; do not assume the client exposes every server badge.

## Inspect ComicInfo and Count

Kavita documents ComicInfo.xml at the root of the comic archive. In authorized copies only, inspect Series, Number, Volume and Count for each file and record each value with its archive. Do not merge fields from different files into one object. Count ideally describes the total volumes or issues, not pages already read. Distinguish a missing field, zero and an uninspectable field.

## Create an incomplete-ownership control

Only when the administrator confirms isolation and restoration and the editor understands XML, set a clear test value in self-made copies, such as a total issue count greater than the two owned issues. Check archive-root location, numbering and XML before saving, recording before and after values. Test values do not describe a real publication. Mark the step unperformed if editing or server rules cannot be verified.

## Observe server scan results

Run or wait for a test-library scan through the current server interface and record completion. Then inspect publication status and owned count separately on the web page: documented ended and completed conditions differ, so ended does not establish a complete local collection. If results differ, first check field locks, series grouping, Count in each file and server version, keeping other conditions unchanged.

## Compare separately when permitted

If permitted and restorable, make a separate control where the test total matches the number of issues recognized by the server, recording before and after values and scan result. Do not change user progress or library access simultaneously. Compare with the server’s recognized volumes or chapters, not just the number of files on disk. If variables cannot be isolated, stop without claiming the completed rule was verified.

## Observe information visible in Manyue+

Return to the same server and normal account in Manyue+ and reopen the series. Record issue count, chapters and status actually visible. If ended or completed badges are absent, mark them not displayed; server data does not guarantee exposure through the connection. Opening an authorized self-made chapter verifies identity but does not prove the whole series is owned.

## Restore and document

Restore test copies and library settings and confirm originals and other users’ progress remain; defer uncertain effects to the administrator. Record server version, each file’s Count, recognized quantity, field locks, server status, Manyue+ observations and skipped steps. Remove private paths and credentials before sharing. This public-documentation guide claims no private-server or device test.

## Check numbering and server grouping

Two archives with ComicInfo may be recognized as separate series or different levels because of Series, Volume or Number. Compare each self-made filename and metadata with the series and issue count actually shown by the server before using its recognized quantity. If one file represents multiple chapters, numbering is duplicated or scanning is incomplete, record uncertainty; two disk files do not automatically mean two recognized issues.

## Record three different states

Use separate columns for publication ended, local collection complete and the test user’s reading completion. The first two concern series metadata and owned items; the last concerns that user’s progress. Mark unavailable values unknown. An ended publication with a missing issue needs no unauthorized download to demonstrate incompleteness; conversely, owning all issues does not mean the user opened every chapter.

## Note field locks and sources

The documented Count rule assumes the field is unlocked. If the server metadata editor shows a lock, record it and do not change production data when effects are unclear. List remote metadata and Count values in other files separately. One observation does not prove a specific source overrode another; leave unknowns for an authorized administrator to investigate.

## Reproducible test values

Reproducible sample: both archive-root ComicInfo.xml files use Series River Demo, Numbers 1 and 2 respectively, and Count 3. If the isolated server groups two recognized issues and the field is unlocked, the documented nonzero Count can indicate ended publication, while two recognized issues are fewer than the total of three and cannot be called complete ownership. As a separate control, change only both Count values to 2 and rescan; if two issues remain recognized, check the completed state. Record actual labels and results for the installed version.
