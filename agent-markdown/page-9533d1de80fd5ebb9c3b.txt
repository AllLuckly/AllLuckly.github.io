English translation of the [Chinese original](<https://allluckly.cn/guides/diaodiao-title-tag-edit-versus-duplicate-import/>), translated on 2026-11-24. Original publication dates, attribution, code and version notes are retained.

Does a recording remain the same file after you change a tag? 调调’s public description says duplicate content is skipped on import, but does not disclose its matching algorithm. This controlled comparison uses a short audio file you are authorized to use: change only the title tag, then compare the original, the edited file, and their import results. Do not turn one observation into a promise about every format or version.

## Prepare two recoverable files

Choose a local MP3, preferably shorter than a minute and far below the 512 MB limit, and confirm it plays in the system file preview. Keep an untouched backup outside the experiment. Make two further copies in a temporary folder, naming them “original tag” and “changed title.” These names identify the files; they are not the titles embedded in the songs. Leave the original-tag copy unchanged and do not delete the backup.

Use a familiar computer or phone tool that edits MP3 tags to open the changed-title copy. Add a recognizable word such as “experiment” only to its song title. Save without re-encoding, trimming, or adjusting volume; if the tool proposes a format conversion, cancel and use one that can edit tags directly. The remaining fields and audio should stay unchanged. If you do not know the tool, practice on a copy and stop if you cannot verify its save behavior; never experiment on the only original.

Play both files in preview, listening to their beginnings and endings, and check that their durations agree. In the tag editor, confirm that the embedded titles actually differ; different filenames alone do not prove that tags changed. Optionally compare checksums with a trusted local tool: different values show a byte difference, not a difference in the music. The ID3 specification describes title as a metadata frame; changing a tag can change bytes without re-recording the audio.

## Set up a comparison record

To avoid treating another variable as the cause, make two rows on paper before importing: original tag and changed title. For each, note location, size, embedded title, duration, and tag tool. Record only information you can actually see; there is no need to install unfamiliar software for the experiment. A size change may simply reflect a different tag length, while unchanged size does not prove identical bytes. If the tool displays a version or embedded cover, note it too, but do not rewrite those fields.

Put the copies where the device can access them, and wait for cloud files to download before starting; a cloud icon in the file picker does not necessarily mean the file is available locally. Preview both files with the device’s built-in tools to reduce the chance of mistaking a download failure for deduplication. Once both previews work, use the two recorded rows as the baseline.

## Import in order and observe

In 调调, import the original-tag copy from Files. When import finishes, find and play it briefly in the music list, making sure it is not another track with the same name already on the device. Record its displayed title and duration, pause, and return to the import entry. Select the changed-title copy. If the system picker cannot see it, check its location and extension in the file manager instead of repeatedly renaming it.

After the operation finishes, check the list again: a second entry may appear, one may remain, or another result may depend on device state. Record the title, entry count, and any actual message; play each entry to verify it. A single entry alone does not prove the app used an audio fingerprint, file hash, or tag for matching. If an older entry already contains the same content, note that confounding factor; do not delete music of uncertain origin just for this experiment. To compare again, use another independently owned recording and keep the import order consistent.

## Check and troubleshoot

The result is a record, not a predetermined claim that deduplication must happen: write down both file titles and durations, import order, list count, and messages. If the tag editor shows different titles but the list shows the same title, verify the selected copies and try reopening the list; this does not prove the tag was not saved. If the edited file will not play, the editor may have converted or damaged it; discard that copy and make another from the backup. If import appears unchanged, also check for an existing item with the same content and for file access permissions.

If neither import yields an identifiable entry, return to the picker and confirm the selected paths, then check that system preview still plays both files. You can use another short recording you own to verify basic import, but keep it separate from the original two comparison rows. If an explicit error appears, record its wording and the step where it occurred before investigating permissions or file availability; avoid changing multiple settings on a guess.

Keep the backup and notes afterwards, and manage the test copies as you prefer. Do not treat editing tags as a reliable way to bypass copyright restrictions or deduplication; results may change with the file and app version. Before comparing different import paths, read the existing guide below and distinguish changing metadata from merely renaming a file.
