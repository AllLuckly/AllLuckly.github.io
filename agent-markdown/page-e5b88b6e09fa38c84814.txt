Distinguish duplicate pages, duplicate files and client reading with test comics.

English translation of the [Chinese original](<https://allluckly.cn/guides/manyue-komga-duplicate-pages-context-observation/>), translated on 2026-11-23. Original publication dates, attribution, code and version notes are retained.

When two comics contain the same image, compare its role in each book and check the server and Manyue+ separately.

## Distinguish duplicate pages and files

Komga’s duplicate-page function uses page hashes to find identical images across books; duplicate files concern entire books and are a separate check. Identical images may be shared copyright pages, recaps or intentional repeated art, not automatic candidates for deletion. Komga warns that removing duplicate pages modifies files. This exercise observes and records only; do not choose delete, auto-delete or ignore actions.

## Prepare safe test material

Ask the administrator to prepare two self-made CBZ copies in an isolated Komga test library they manage or are authorized to use. Give each three images, one shared self-made test page, and distinct A and B markers on the others. Retain original archives and a server-data backup; record filenames, page counts and positions of the shared page. Without a backup, permission or administrator support, stop at preparation and avoid production bulk actions.

## Confirm the page-hash prerequisite

Komga requires page hashing in libraries for duplicate-page detection; this is separate from whole-file hashing. Ask the administrator to check the current version and existing test-library settings, consider resource cost and wait for test-book analysis. This exercise does not require enabling a new task on production libraries. If page-hash status cannot be confirmed, mark server detection not performed rather than guessing from filenames.

## Record reading baselines

In the Komga web interface, inspect both test books and record series, title, page count, markers before and after the shared page, and page order. In Manyue+, use the same server and account and check that the same pages are readable. Record any existing page-count difference separately; do not modify archives to force agreement. Similar covers, page numbers or file sizes do not establish that whole books are duplicates.

## Inspect the server duplicate-page result

Have the administrator open Server Settings → Duplicate Pages in Komga, find the self-made shared page among new detections and open Matches. Record involved books, page positions and actual image. Labels may vary by version. Without permission or confirmed identity, mark the group unconfirmed. Do not infer that two whole books are identical simply because one image appears twice.

## Judge each page in context

Inspect the content before and after the shared page in both test books. It could serve as a cover, copyright notice, recap or chapter separator. Identical pixels may still have a legitimate role in different contexts. For real comics do not delete copyright information, repeated spread elements or original structure because a detector reported a match. A person authorized to organize content should consider rights, backup and purpose first; this exercise performs no deletion.

## Check the same pages in Manyue+

Reopen both test books under the same account in Manyue+, using image markers to check the shared page and its neighbors. Record app positions and whether they correspond to server results. If the client lacks a duplicate-page management interface, that is an unobserved capability; do not assume automatic deduplication. If page counts differ, check version, import source and actual file identity before changing archives or forcing a server refresh.

## Separate resemblance from exact identity

Use the shared test-page copy for a group whose identical content can be confirmed. If another picture looks similar but has different dimensions or file contents, record it separately and do not assume Komga matches it in the same way. Server hashes, visual resemblance and whole-file identity are three distinct concepts. Without inspecting the actual algorithm and result, do not claim a particular hash or complete detection of near-duplicates.

## Record exceptions and unperformed work

If the administrator sees no result, check completed page analysis, page hashing for the correct library and server identity. Do not change production settings or enable automatic deletion to troubleshoot. Record time, server version, book aliases, candidate group and app display. If a test page did not match, record that outcome rather than a predicted pass. Exclude private server addresses and unauthorized comic images from support reports.

## Make a table without original images

Write one row per test book with markers before, on and after the shared page, plus server and Manyue+ display. Use self-made markers or sanitized descriptions rather than copying copyrighted pages. If one picture appears at the start of one book and end of another, record both positions; do not equate match count with deletable page count.

Keep the same test account and library throughout. For similarly named series, identify the edition by page count and self-made markers. If identity remains uncertain, mark it pending and ask the administrator. This table checks observation completeness; it does not replace page review or an authorized person’s decision about retention.

## Finish without changes

Leave the management page and verify that no ignore, manual delete or auto-delete action was chosen. The administrator retains or cleans up test copies according to normal practice. If necessary compare backups and test archives to confirm originals and production libraries remain unchanged. Record web detection, Matches details, Manyue+ readability and unperformed steps separately. The guide is based on public documentation and claims no private-server or device test.
