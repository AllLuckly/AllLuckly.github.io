## Make original transparency controls

Externally design three marked regions intended as opaque, fully transparent and partially transparent, preserving the original settings. An editor’s checkerboard may be a display aid rather than stored pixels; inspect exported data instead of treating an editor screenshot as a transparent file. Fix dimensions at four hundred by three hundred and put markers in an opaque area. Note that antialiased text may introduce intermediate alpha values so extra reported values have an explanation.

## Understand a truecolour transparency key

Export A as truecolour type two with tRNS specifying one RGB key, such as pure green, only if the tool supports it. The key matches the entire RGB sample tuple, not every greenish pixel. Matching pixels are fully transparent and others opaque; this key cannot assign an arbitrary half-opacity to a pixel. If the tool actually outputs type six, record RGBA rather than insist on tRNS because an export button mentioned transparency.

## Record RGBA’s separate alpha sample

Export B as type six with eight bits per sample: alpha is separate from RGB. Alpha zero means fully transparent, two hundred fifty-five fully opaque, and intermediate values partial transparency. A value of one hundred twenty-eight is one hundred twenty-eight over two hundred fifty-five, near rather than exactly one half. It is not green intensity, and four eight-bit channels do not total eight bits per pixel. Leave premultiplied internal buffers outside this exercise rather than confuse file samples with library memory layouts.

## Keep indexed transparency distinct

Optional indexed type-three C can associate alpha with palette entries through tRNS; do not transfer type-two’s single fully transparent RGB-key restriction to indexed transparency. Record which index maps to which palette colour and alpha: index is not alpha itself. A and B suffice, with C conditional on tool support and reports. Do not invent success or insert tRNS arbitrarily into type six as a second transparency system; the specification restricts that chunk for alpha-bearing types. No binary editing is required.

## Compare compositing on light and dark backgrounds

Open A and B through an existing local path and compare the same regions on light and dark backgrounds when the actual interface offers them. Otherwise record the available condition. Fully transparent regions reveal the background; partially transparent colours change composited appearance with it, without proving source RGB was rewritten. Use opaque markers to confirm file identity. A screenshot usually captures composited appearance and cannot recover a source alpha report by itself. Retain observations and source fields separately.

## Inspect antialiased edges around a colour key

If A shows a green fringe, inspect whether antialiasing created pale-green edge pixels unequal to the exact key; similarity does not make them transparent. Per-pixel alpha in B can represent smoother edges, but source and compositing still matter, so a type change does not guarantee removal of every fringe. Check centres and edges using original shapes before library-wide changes. If a tool flattened onto white earlier, reader themes cannot automatically recover discarded transparency.

## Check white backgrounds and missing evidence

An invisible patch on white does not establish missing content: change an available background or inspect alpha externally. Three channels with transparency may involve type-two tRNS rather than a false report. Distinguish an absent field from a tool that did not expose it; unknown is not none. Convert copies while preserving the transparent source, avoiding flattening the only original.
