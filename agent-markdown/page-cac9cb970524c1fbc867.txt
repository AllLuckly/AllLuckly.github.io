Use a short recording you own to record a playback anchor and observe actual sound and app position before and after locking.

## Prepare an owned short recording and baseline

Choose a one- or two-minute recording you made or may use, with two distinguishable spoken sentences A and B. Preserve the original and check battery and a suitable listening volume. The public listing describes common audiobook formats, but does not guarantee every codec or lock-screen state. Import the sample in the installed version and first confirm audible content in the foreground.

## Record position and audio output

Near sentence A, record file identity, the displayed playback time, the actual short phrase heard and the current audio destination. Time is a positioning aid; editing and encoding can affect displayed timing, so the actual phrase is a separate anchor. If using Bluetooth headphones or an external device, record it without changing the connection and introducing another variable.

## Confirm playback before locking

Check whether the displayed player state agrees with actual sound, then lock the device through its ordinary control. Do not assume locking pauses or continues playback. Record whether sound remains audible, any interruption and observation time. If the user does not wish to lock, the sample cannot play or system configuration prevents it, mark the step untested.

## Observe only system controls actually shown

After locking, observe whether relevant media controls or Now Playing information are displayed. If absent, record not observed rather than claiming every system provides them. If a clear pause or play control is present, operate it once only if the user wants to, observing sound and displayed state. Avoid repeated taps and assumptions about progress synchronization. System media controls are a system interface whose behavior depends on app and OS version.

## Unlock and return to the same recording

Unlock normally and return to Book Isle. Confirm the file and chapter are the original sample, then record player time and the actual current phrase. Keep pre-lock A, audible behavior during lock and post-unlock B as separate observations. Even if time advances, verify that audio is actually playing. If it returns to the beginning or another chapter, preserve the first result rather than jumping to the expected point and claiming automatic resume.

## Troubleshoot in layers without erasing data

If the timer advances but no sound is heard, first check the original output destination and volume. If the timer stops, record pause, system interruption or unknown state without assuming one mechanism. Change one clear condition, such as returning to the foreground and replaying the same segment. Do not simultaneously reinstall, replace the recording and change headphones. Mark the cause unknown when the system or app does not identify it.

## Record a repeatable timeline

In a local table list foreground playback at A, first locked observation, one pause only if actually operated, and return after unlocking. Record actual time, displayed state, words heard and output destination separately for each row. Hearing the end of A after locking while the interface later shows paused does not prove continuous playback for the entire locked interval; final pause does not prove immediate pause either. Mark an indistinct phrase unknown. Do not repeatedly increase volume or switch headphones and still call it the same condition. The table need not contain private audio or notification screenshots.

## Separate interruptions from the file itself

If the original recording also has silent or clipped sections in a system player, preserve and inspect that file before deciding what the Book Isle observation establishes. Do not label source silence a lock-screen failure. If the original is clear but audio disappears while locked, record output, foreground state and any system message, then make one foreground comparison with the same segment. An absent app control and whether sound continues are separate observations; neither proves the other.

## Use clear anchors for a second return

If the user wants one repeat, return to sentence A of the same original recording and record current system output, volume and foreground state, then repeat the same lock-and-return procedure once. Do not simultaneously start other audio, disconnect headphones or change system permissions. If those events actually occur, list them as separate conditions. Compare phrases actually heard and player times: different results show only that observations differed under recorded conditions and do not establish a cause; matching results cover only this sample and device. If the specific spoken sentence is unclear, stop or use a comfortable volume rather than forcing the user to use a higher level for a test.

If a call or other audio interrupts while locked, record it as an extra event and, if the user wishes, perform a separate comparison without it. Do not combine both actual observations into one uninterrupted playback.

## Restore the device and keep observations

Restore pre-test volume, output and lock settings, and confirm the original audio and reading records remain. Record device and system versions, app version, sample anchors, lock-screen sound, control visibility, actual actions and reopened position; mark unperformed steps untested. Do not attach private recordings or account data to feedback. This exercise uses public audiobook capability and Apple system guidance and claims no physical-device, background or lock-screen test.
