Use one authorized EPUB to compare SMB share, folder and file access with opening in Book Isle, locating differences after connection.

## Prepare a known-readable test book

Choose a small authorized, nonprivate EPUB in your own SMB share. Keep the original and place a test copy in an existing library path. Record the share name, relative path, size, title and a nonprivate passage. Open the copy locally on the server using an existing reader and check the recorded text anchor. This establishes that the sample opens, not that the whole book is intact. If it cannot open there, address the file first. Do not publish addresses, usernames, passwords or private titles.

## Confirm the source used in Book Isle

Locate the existing SMB private library in Book Isle and verify its destination share, account and the test book’s path. Use account identity only locally, not in a public record. Public information lists SMB private-library browsing and reading; availability also depends on the installed version, permissions and membership. A source root is not the entire server. Resolve an unclear target before continuing instead of creating multiple similar sources.

## Observe listing and content separately

In Book Isle, enter the source and folder actually displayed. Record whether the share appears, whether the folder opens and whether the EPUB name and size are visible. If selectable, use the current interface to open or download it once and check the text rather than the cover alone. Record listing, completed download and opened content as three separate results. A listing does not automatically prove file access, and a cover does not prove readable text.

## Compare with the system Files app

On the same device and network, follow Apple’s Files guidance to connect to the same server and share. For a registered user, use the same authorized account as Book Isle and first verify that the system is not connected as another account or guest. Browse to the same path, check file access and, where the system permits, open the test copy. Success in Files establishes that this connection could read it, not that both apps use identical caches or configuration.

## Narrow the problem using observations

If neither location enters the share, first check that the server is running, the address is reachable and the current account is authorized; do not guess that EPUB format is responsible. If the share opens and folder is visible but both cannot read the file, have an authorized administrator inspect both share and file-level read access. NAS permission models and messages vary; do not assume identical rules everywhere. Grant only necessary access rather than making the entire library public.

## Check client conditions only when a difference appears

If Files reads the book but Book Isle cannot, reconfirm the same account, share, file and network, and record the Book Isle version, membership state and redacted error. Another account’s success does not establish this account’s access, and one client’s success does not by itself prove a defect in the other. If the original file is readable but cannot be read as a book, check its format and actual error; compare a second known-good authorized EPUB without overwriting the original.

## Record the final results

Create a table for the server itself, system Files app and Book Isle, with separate share, folder, file and text outcomes; mark inapplicable checks untested. Record time, network type and the one condition changed at each step without credentials. When asking for help provide redacted errors and versions rather than uploading a private book. Remove the test copy through the existing management process and confirm the original remains unchanged. This article does not claim physical-device or NAS testing.

## Example: two outcomes for the same path

Suppose the server itself opens the practice book, Book Isle lists the filename but reports an opening error, and the system Files app using the same account and path also reports no read access. This is evidence that listing and file reading have different outcomes. Ask an administrator to inspect the user’s access to the share, folder and file, then retest the same sample. A visible filename does not establish download success; do not promote the account to administrator. Follow the server’s own documentation for its interface and effective-permission calculation.

Alternatively, Files may read and open the same file while Book Isle still reports failure. Check whether Files retained an old connection, guest identity or different username. If needed, disconnect that test connection using the system interface and reconnect with the confirmed account. Do not delete the Book Isle source or erase all reading records. Once the accounts really match, record the Book Isle entry and error and contact app support; the difference alone does not establish the root cause.

## Distinguish download from opening offline

If Book Isle offers a download entry, record its actual state and file size before and after, and confirm in the app that the download completed. Before testing offline, establish that the copy is actually available locally and note which network connection you will turn off and how to restore it. A cached remote listing is not necessarily a complete book. Try the same book after disconnecting; on failure, record that it did not open under those conditions, without concluding that the server file is corrupt.

Restore connectivity, return to the library and compare the same test file. If it opens online but not offline, retain the two observations, times and download state and read current app prompts; do not delete the remote file to force a download. This describes observed outcomes and does not promise identical offline behavior for every membership, version or format. Restore the device’s original network settings afterwards.
