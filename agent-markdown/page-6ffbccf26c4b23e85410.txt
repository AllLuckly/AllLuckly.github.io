A browser login page is only one part of a proxied comic service. ManYue also needs the appropriate catalogue and image endpoints, whose paths and redirects may behave differently. Check the address in parts and test real app access; there is no universal proxy configuration for every service.

## Identify the connection type first

Identify whether the connection is Komga, Kavita, OPDS or WebDAV. Their endpoint types differ. Obtain the intended application base address from the service maintainer and separate protocol, host, port and subpath. A browser’s current book-detail URL can contain web routes or temporary parameters and is not necessarily a suitable connection base.

## Inspect the components of the address

Check scheme, hostname, any non-default port and trailing path separately. Changing the letters from HTTP to HTTPS does not create an encrypted endpoint, and another server’s example port may be irrelevant. Remove copied whitespace or punctuation. Use a placeholder domain when illustrating the structure publicly while retaining the known actual address for your own test.

## Distinguish the public prefix from a web route

A public subpath must be handled consistently by proxy and backend. Observe whether browser navigation retains the prefix and where images load from. The required base depends on the selected service, not on an arbitrary web route. Avoid trying large numbers of guessed paths. Correct credentials cannot compensate for an endpoint that points to the wrong location.

## Check whether browser access depends on redirects

Browsers may follow scheme or hostname redirects and extra authentication pages that an app connection does not reproduce. Use the maintainer-confirmed final service endpoint and check its supported authentication flow. Do not embed credentials in a URL or treat a temporary post-login link as permanent. Record redirects without sharing identifying or sensitive query parameters.

## Check catalogue and pages in sequence

After saving a test connection, check authentication, a known catalogue item and actual chapter images. Catalogue success with image failure establishes only partial access. Investigate page requests, forwarding and account rights. Test downloading if the service permits it. Change one address component at a time and report the failing stage and message precisely.

## Resolve certificate issues at the service boundary

For certificate-related failures, check device time, hostname and the server’s certificate deployment with its maintainer. Certificate validation and a wrong application subpath are separate issues. Support for a particular private certificate depends on the installed version and environment; do not assume a universal bypass switch. Correct the intended service setup before repeating the app test.

## Compare a known direct route when available

If you manage the service and already have a working local route, compare it with the proxy using the same account and book. No new public exposure is needed. A direct success narrows the investigation to the proxy route; failure on both calls for service and permission checks. Clearly label test connections and retain the final verified endpoint with its check date.

## Questions and completion criteria

Why can a login page work while API access fails? Their routing and authentication steps can differ. Should you always remove a subpath? No; the deployment determines the correct prefix. Completion means a known endpoint for the chosen service and verified authentication, catalogue and pages. Share redacted address structure and the failure stage rather than credentials or temporary tokens.
