Seeing a Jellyfin library does not establish that an account permits every playback path. Check one authorized clip in stages.

## Separate library access and playback conditions

iCouldPlay publicly supports connecting to Jellyfin, browsing and playback. Jellyfin user-management documentation lists media playback, audio/video playback requiring transcoding, and video conversion without re-encoding as separate permissions. Signing in or seeing a film does not establish that every playback path is allowed; a single failed playback does not by itself prove a permission problem. Record each stage with one authorized account.

## Prepare an account and short clip

Choose a Jellyfin server you manage or are authorized to use, a normal account already allowed to view a test library, and a self-made or authorized short clip. The administrator has permission to inspect user settings and active sessions; the account holder enters credentials personally. Record server alias, clip name or self-made picture marker, time, device and iCouldPlay version. Do not share passwords, tokens, private addresses or other users’ activity.

## Confirm a normal connection

In iCouldPlay use the Jellyfin source settings actually offered by the installed version, the administrator-provided secure address and authorized account to connect normally. For an existing source, confirm server and account without deleting or rebuilding it. Stop and record certificate or login errors; do not bypass warnings or repeatedly guess passwords. A visible test-library listing is a listing result, not proof that the clip played.

## Inspect the same web entry

The account holder signs into the Jellyfin web interface on the same server and account, enters the same test library and identifies the clip by title, duration and self-made opening marker. Record listing and actual playback start separately; a similar poster alone does not establish the same file. If the web is unavailable, check server, account and existing access without asking the administrator to expand permissions.

## Inspect current playback settings

An authorized administrator checks the test account’s existing media playback, audio/video transcoding and conversion without re-encoding options read-only, using labels shown in the current server version. The administrator can provide sanitized allowed, denied or unknown results instead of the full account screen. Do not change production permissions, enable media deletion or create an administrator merely to pass the test.

## Actually play in iCouldPlay

Open the confirmed clip in iCouldPlay and record playback start, picture, sound and stop position. If it fails, record the exact sanitized message and stage. One successful clip establishes only that observation, not support for every format. If authorized, the administrator can identify the corresponding device and time in the server dashboard and record the displayed processing type; mark unknown if no session can be matched.

## Separate transcoding and non-transcoding paths

Jellyfin documents that account policy can restrict playback requiring transcoding, with another option for conversion without re-encoding. The required processing also depends on source, client, server and current selections. It cannot be determined from extension, resolution or account setting alone. Compare account configuration with processing only when the administrator verifies the matching session and its type. Without that evidence do not attribute failure to a transcoding permission.

## Compare web and iCouldPlay without changing permissions

If the web plays and iCouldPlay does not, check the same film, account, network, time, and audio and subtitle choices. Different clients can request different processing. The administrator inspects the current session and existing settings and records both results. Even different reported processing does not automatically establish an app defect. If no matching session is verifiable, mark pending rather than changing permissions to manufacture a comparison.

## Identify the stage of failure

Use four rows: connection, test-library listing, opening the film, and picture and sound. For connection failure check secure address and account. If listing works but opening fails, record the error and ask the administrator to inspect existing playback settings. If playback starts then stops, record the time and network. Never modify server configuration or delete source media without authorization. Remove addresses, credentials and personal viewing history before contacting support.

## Build verifiable evidence rows

Give each web or iCouldPlay attempt a row with the same clip marker, account alias, network, start time, selected audio or subtitles and actual result. Put the administrator’s configuration observation in a separate row, identifying whether existing settings were inspected or unavailable. Do not describe “may need transcoding” as a server-reported fact. If multiple devices play at once, the administrator must match device and time without viewing or recording other people’s media details.

If current policy disallows a processing path, respect the administrator’s rule, record the limitation and seek authorized compatible content. Do not advise readers to enable permissions or weaken protections themselves. Even when policy allows processing, damaged media, network or server state can still cause failure; continue from the actual error stage.

## Finish and preserve state

Stop your own test session and confirm account settings, production library and source file remain unchanged. Record sanitized current permission findings, web and iCouldPlay stage results, server-session evidence and unperformed items. If settings cannot be inspected, explicitly mark unknown; do not report a recommended check as completed. This public-documentation guide claims no private-server connection or iCouldPlay physical-device test.
