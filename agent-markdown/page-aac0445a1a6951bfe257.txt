Compare your own small source video and downloaded copy while recording object identity, ETag and checksum algorithm separately.

## Prepare a known-source short video

Choose an authorized short video, retain the original and record its size, duration and opening. Confirm the upload target is S3 or compatible object storage you manage. Do not publish private video, bucket names, keys or signed URLs. Public iCouldPlay information supports S3-compatible storage but does not promise an ETag or checksum display.

## Check object identity and upload method

In an authorized storage-management interface confirm bucket, key, actual size, version identifier and upload method. If the interface does not indicate multipart upload, record unknown rather than inferring it from a filename. Where versions exist, identify the intended current version first without overwriting or deleting an object. Metadata and checksum support vary among S3-compatible services; consult the provider’s documentation.

## Understand the ETag boundary

Amazon S3 documents that a multipart-upload ETag is not the MD5 of the entire object, and an ETag for some single-upload encryption modes is not necessarily the whole-file MD5 either. A local MD5 differing from the ETag alone therefore does not establish video corruption. An ETag is a server-returned object label whose meaning depends on service, upload and encryption. Do not assume every Amazon S3 implementation detail applies to compatible services.

## Compare the same whole-file algorithm

Download the object using a trusted storage tool to a new test path without overwriting the original. Use the same whole-file checksum algorithm on each, for example macOS Terminal `shasum -a 256` followed by the appropriate file path, or another trusted tool. Compare both algorithm names and complete results. Matching results provide strong evidence of identical bytes, not a guarantee that video content or playback experience is correct.

## Check actual playback in iCouldPlay

Open the same storage source in iCouldPlay, confirm path, filename and duration, and play the beginning and a middle passage against known scenes. Normal playback, a complete download and a whole-file checksum are distinct outcomes; a cover or a few seconds of playback do not replace a whole-file comparison. On failure record network state and actual feedback. Do not claim the app calculated a hash or automatically verified the ETag.

## Troubleshoot differences in layers

If the SHA-256 values differ, first check that the same object version was compared, the download completed and the correct path was selected; then inspect provider-supplied checksum information. Change one condition at a time. Do not overwrite the only original by reuploading or directly change bucket permissions. If hashes match but playback fails, separately investigate file format, client and network and retain redacted results. Afterwards remove only the test copy. No device or storage test is claimed.

## Keep a reproducible comparison ledger

Use one row each for the local original and newly downloaded copy with a redacted name, byte size, retrieval time and SHA-256 result. Record the provider’s ETag and object version separately. Do not place an ETag in the SHA-256 column. If a tool uses another algorithm or shows only a truncated value, confirm the full algorithm and output before comparing; otherwise write unable to compare. Matching prefixes alone do not establish equality.

In macOS Terminal, type ` shasum -a 256  `, drag the file into the window so the system fills its path, and press Return. Repeat for the second file. Do not replace the file path with a remote link containing secrets or publish complete terminal output, since paths can reveal private information. Large files take time; mark a cancelled computation incomplete. On error inspect path and read permission rather than writing a guessed hash.

## Choose the next step based on observed results

For example, equal sizes but different SHA-256 values establish only that the comparison differs. Check the intended object version, download completion and whether a similarly named old file was selected, then download to another non-overwriting location if needed. For a provider checksum, establish whether it is whole-object or composite and identify algorithm and encoding before comparing. Different checksum types cannot be compared directly.

If both size and SHA-256 match but iCouldPlay pauses during playback, separately record device network, time and actual feedback. A completed byte comparison and streaming experience under current network conditions are distinct checks. If the version opened in iCouldPlay is uncertain, mark it unconfirmed rather than drawing a conclusion about the app. An administrator can inspect redacted server records as needed; do not expose tokens or temporarily make the bucket public for testing.

## Clean up and restore

After checking, confirm the original video and online object remain, then remove only the downloaded test copy using your storage-management process. Do not delete old object versions or interrupt someone else’s upload. If file identity is uncertain, retain it and ask the administrator. Record steps actually performed, their results and untested items. This exercise uses an external checksum tool; it does not claim iCouldPlay has that feature built in. If a complete object cannot be downloaded, retain the confirmed size and version and mark full verification unperformed; partial playback is not a substitute.
