### Introduction

### Testing with Xcode

Xcode provides facilities for extensive software testing. Testing primarily checks a project's robustness and reduces bugs, helping you distribute and sell a product sooner. Checking expected behavior improves user satisfaction. Tests can help you develop faster and avoid wasted effort.

![1](<https://allluckly.cn/images/blog/tuogao/tougao38/1.png>)

### Contents

This document explains the testing features included in Xcode. XCTest is linked automatically when tests are added.

1. Quick start: Since the introduction of XCTest in Xcode5, configuring project tests has been simplified, and tests can be managed and run automatically from the navigator.  
 2. Performance testing: Xcode6 and later let you track and measure changes in the performance of basic units.  
 3. UI testing: Xcode7 adds the ability to test the user interface.  
 4. Continuous integration and Xcode Server: Run Xcode tests through command scripts or configure bots to run them automatically on Xcode Server on a Mac.  
 5. Modernization: Xcode includes migration support for projects with OCUnit tests.

### Prerequisites

You should be familiar with application design and programming concepts.

### Editing and rerunning tests

This sample project is a calculator. You need to check the correctness of addition, subtraction, multiplication, and division, along with its other functions. Add and write tests in the project for whatever you want to test; doing so requires a code structure that supports testing. For example, add instance declarations and class imports in SampleCalcTests.m.

```
// Import the application specific header files#import "CalcViewController.h"
#import "CalcAppDelegate.h"@interface CalcTests : XCTestCase {
// add instance variables to the CalcTests class@private
   NSApplication       app;
   CalcAppDelegate     appDelegate;
   CalcViewController calcViewController;
    NSView              calcView;

@end
```

Give the test method a descriptive name, such as testAddition, and add the implementation.

```
- (void) testAddition
{
    //obtain the app variables for test access
    App = [NSApplication sharedApplication];
    calcViewController = (CalcViewController)[[NSApplicationsharedApplication] delegate];
    calcView = calcViewController.view;

    [calcViewController press:[calcView viewWithTag: 6]];  // 6

    [calcViewController press:[calcView viewWithTag:12]];  // =
    XCTAssertEqualObjects([calcViewController.displayField stringValue],@"8", @"Part 1 failed.");
    [calcViewController press:[calcView viewWithTag:13]];  // +
    [calcViewController press:[calcView viewWithTag: 2]];  // 2
    [calcViewController press:[calcView viewWithTag:12]];  // =
    XCTAssertEqualObjects([calcViewController.displayField stringValue],@"10", @"Part 2 failed.");
}
```

### Using setUp() and tearDown()

When Xcode runs a test bundle, it executes all the methods in the test class. If each method needs an initialized object, initializing it separately creates duplicate code. XCTest provides two instance methods for setting up and tearing down test instances. Put shared setup and cleanup there. Using setup and teardown is straightforward.

```
- (void)setup

{

    [super setUp];

    // Put setup code here. This method iscalled before the invocation of each test method in the class.

   // obtain the app variables for test access

  app = [NSApplication sharedApplication];

   calcViewController = (CalcViewController)[[NSApplicationsharedApplication] delegate];

   calcView = calcViewController.view;

}
```

Setup runs before the test method, so the test can use properties that have already been initialized.

![1](<https://allluckly.cn/images/blog/tuogao/tougao38/12.png>)

### Overview

This brief quick start shows that adding tests is straightforward. There are still a few points to keep in mind:

1. Xcode supplies most of the basic test configuration. When you add a new test, it automatically adds these test methods. Individual test methods can be found and run from the test navigator.
2. The test navigator makes it easy to find and edit test methods. Run them from the navigator or the gutter; a failed test displays a failure indicator in the gutter.
3. One test method can contain several assertions, which together produce a single pass or fail result. Tests can be as simple or complex as needed. Put shared code in the setup and teardown instance methods.

## Basic testing

Testing checks whether application and library code runs successfully against expected results. After performing operations, a test may inspect an object's instance variables or determine whether particular boundary conditions cause a specific exception.

### Defining the scope of testing

Software is composed of many units: small components combine into larger, more capable components until the project's requirements are met. Good testing covers the behavior of that entire composition. Unit tests usually address smaller, function-level components, while XCTest lets you write tests for components at any level of the hierarchy.

You decide what constitutes a component under test: a single method or a group of methods serving a basic purpose. For an arithmetic example, see Apple's official demo. Different methods handle interactions between tableView content and the data structure containing list names. Each method contributes to application behavior and can be tested. The component's expected behavior should be fully defined, whether the test succeeds or fails.

The more thoroughly you divide application behavior into components, the more effectively you can test its details against reference expectations, particularly as the project evolves. A large project with many components needs many tests for comprehensive coverage. Tests should run quickly where possible, although large tests may be slower. When a failure occurs, small, quick tests make diagnosis and repair easier.

Designing tests for project components is the basis of test-driven development, or TDD: write the test logic before the code it tests. This lets you define requirements and boundary conditions before implementation. After writing the tests, develop algorithms that pass them. Once the code passes, you have a foundation for improvement and confidence that later test runs will detect changes in expected behavior that could introduce product bugs.

Even without test-driven development, tests help improve features and functionality by reducing bugs introduced during changes. Test a working application to ensure later changes do not alter its behavior. When fixing a bug, add a test to verify the fix. Tests should exercise both expected success and expected failure to cover boundary conditions.

## Note: Adding tests to a project not designed for testing may require refactoring some code to make it easier to test. Writing Testable Code contains useful, concise guidance.

Components may include interactions between parts of your application. Some tests can take a long time, so you may prefer to run them periodically or only on a server. Organize and run tests in different ways to meet different needs.

### Performance testing

Tests can check a component's functionality and record its performance. XCTest APIs measure time-based performance, allowing you to track improvements or regressions in a method or function.  
 To determine whether a performance test succeeds or fails, it needs a baseline for comparison. The baseline is the average elapsed time calculated across 10 runs. A result that differs too much from that baseline fails.

## Note: The first performance-test run reports failure because the baseline is not yet known. Once a measurement baseline is set, XCTest reports success or failure and provides detailed results.

### User-interface testing

Functional and performance tests are generally called unit tests, where a unit refers roughly to a component or the smallest module. Unit tests mainly check that related components interact as expected. From a design perspective, they are written during development to capture your expectations. Users interact with the interface backed by your source code. Such interactions generally combine an entire subsystem to achieve the expected behavior. These are difficult to cover with unit tests; specialized tests for them are called UI tests.  
 UI tests are closer to the user's experience. Add simulated events, capture the objects' responses, and check correctness and performance in much the same way as unit testing.

### Application tests and library tests

Xcode supports two kinds of testing: application tests and library tests.  
 Application tests check components of app code, as in Apple's official demo. Use them to ensure that UI controls remain in the expected positions and that controls and controller objects work correctly with model objects.

Library tests check the behavior of independent code that is not running inside an application. They let you combine and test library components, usually objects and methods. They can also stress-test code under extreme conditions unlikely to occur in a running app. Such tests help produce robust code that behaves correctly even in unexpected circumstances.

### XCTest—the Xcode testing framework

XCTest is the testing framework used in Xcode5 and later. If you previously used OCUnit, the two may look similar. XCTest is its more modern replacement, integrates more closely with Xcode, and provides a foundation for future testing improvements. Xcode adds XCTest.framework to your project rather than SenTesting.framework. The framework supplies APIs for designing and running tests in code.

## Note: Xcode includes a migration assistant for projects containing OCUnit tests. For details on conversion to XCTest, see Transitioning frome OCUnit to XCTest.

### Where tests run

As you begin creating tests, keep these approaches in mind:

1. Focus on testing the most fundamental functions, model classes, and methods that interact with controllers. A high-level application diagram will likely contain Model, View, and Controller categories, a familiar design pattern to Cocoa and Cocoa Touch developers. Writing tests that cover all Model classes gives you confidence that the app's foundations are well tested before you write Controller Classes tests and move into more complex parts of the application.
2. As an alternative starting point when writing a framework or library, begin with the application's interfaces and work inward to its internal classes.

### The structure of a test class

A test class contains the following basic structure:

```
#import <XCTest/XCTest.h>

@interface SampleCalcTests : XCTestCase

@end

@implementation SampleCalcTests

- (void)setUp {

[super setUp];

// Put setup code here. Thismethod is called before the invocation of each test method in the class.

}

- (void)tearDown {

// Put teardown code here. Thismethod is called after the invocation of each test method in the class.

[super tearDown];

}

- (void)testExample {

// This is an example of afunctional test case.

// Use XCTAssert and relatedfunctions to verify your tests produce the correct results.

}

- (void)testPerformanceExample {

// This is an example of aperformance test case.

[self measureBlock:^{

// Put the code you want tomeasure the time of here.

}];

}

@end
```

The test class is implemented in Objective-C. Its implementation includes basic instance methods such as setup and teardown. These methods are required. If all test methods need the same code, customize setup and teardown to contain it; that code runs before and after each method. You may also add class-level setup (+ (void)setUp) and teardown (+ (void)tearDown), which run before and after all methods in the class. Xcode's test execution sequence clarifies their use.

## The test execution sequence

During a test run, XCTest finds all classes inheriting from XCTestCase and runs their test methods. For each class, it first runs the class setup method. It creates a fresh instance for each test method and runs that instance's setup method. After the test method, it runs the instance teardown method. This repeats for every method. After the final instance teardown, Xcode runs the class teardown method and proceeds to the next class. The sequence continues until every method in every test class has run.

## Writing test methods

Write tests as methods in a test class. A test method is an instance method whose name begins with test, takes no parameters, and returns void. For example, TestColorsRed calls project code and uses assertion APIs to report when it does not produce the expected result. A function might return an unexpected value, or an inappropriate method call might throw an exception. See XCTest Assertions for these cases. Import the correct headers into the test class so the methods can access the code under test. Xcode runs each method independently. Each must therefore prepare and clean up its supporting variables, structures, and objects that interact with the target API. If every test method shares the same setup or cleanup, put it in the setup and teardown instance methods, which always run. See Test Class Structure.

Here is a test-method template:

```
- (void)testColorIsRed {
   // Set up, call test subject API. (Codecould be shared in setUp method.)
   // Test logic and values, assertions reportpass/fail to testing framework.   // Tear down. (Code could be shared intearDown method.
}
```

Here is a simple test that checks whether a CalcView instance was successfully created for SampleCalc. See Quick Start.

```
- (void) testCalcView {

   // setup

   app = [NSApplication sharedApplication];

   calcViewController =(CalcViewController)[NSApplication sharedApplication] delegate];

   calcView = calcViewController.view;

   XCTAssertNotNil(calcView, @"Cannot findCalcView instance");

   // no teardown needed

}*
```

## Writing tests for asynchronous operations

Tests run synchronously: the next one starts only after the previous one ends. Increasingly, however, the code under test executes asynchronously. To handle such methods and components, Xcode6 adds support for sequencing tests of asynchronous execution, waiting for a callback or timeout before completing. For example:

```
// Test that the documentis opened. Because opening is asynchronous,
// use XCTestCase'sasynchronous APIs to wait until the document has
// finished opening.-(void)testDocumentOpening
{  // Create anexpectation object.
    // This test only has one, but it'spossible to wait on multiple expectations.
   XCTestExpectation documentOpenExpectation = [selfexpectationWithDescription:@"document open"];
    NSURL URL =[[NSBundle bundleForClass:[self class]]
                             URLForResource:@"TestDocument"withExtension:@"mydoc"];
    UIDocumentdoc = [[UIDocument alloc] initWithFileURL:URL];
    [docopenWithCompletionHandler:^(BOOL success) {
       XCTAssert(success);
       // Possibly assert other things here about the document after it hasopened...
       // Fulfill the expectation-this will cause -waitForExpectation
        // to invoke its completion handler andthen return.
       [documentOpenExpectation fulfill];
    }];
    // The testwill pause here, running the run loop, until the timeout is hit
    // or all expectations are fulfilled.
    [selfwaitForExpectationsWithTimeout:1 handler:^(NSError error) {
       [doc closeWithCompletionHandler:nil];
    }];
}
```

For more information on asynchronous operations, see XCTestCase+AsynchronousTesting.h in XCTest.framework.

## Performance testing

A performance test runs a code block 10 times and collects the average execution time and standard deviation. The measured average is compared with a baseline to determine success or failure. **Note: A baseline is the reference value you specify to determine whether a result passes. The report UI provides controls to set or change it.** Performance testing uses the newer XCTest method APIs available from Xcode6 onward.

```
- (void)testPerformanceExample{
    // This is an example of a performance testcase.
    [self measureBlock:^{
        // Put the code you want to measure thetime of here.
    }];
}
```

The example below briefly demonstrates a performance test written for a calculator application. XCTest iterates a measureBlock to measure elapsed time.

```
- (void) testAdditionPerformance{

    [self measureBlock:^{

        // set the initial state

        [calcViewController press:[calcViewviewWithTag: 6]];  // 6

        // iterate for 100000 cycles of adding2

        for (int i=0; i<100000; i++) {

           [calcViewController press:[calcViewviewWithTag:13]];  // +

           [calcViewController press:[calcViewviewWithTag: 2]];  // 2

           [calcViewController press:[calcViewviewWithTag:12]];  // =

        }

    }];

}
```

Running a performance test adds information to the test navigator. Click it to see the measured values. The result includes controls to use a measurement as the baseline for future comparisons. Baselines are stored per device configuration, so the same test on different devices has different baselines, depending on processing speed, memory, and other characteristics.  
 Note: Performance tests report failure on the first run, and continue doing so until a baseline is set for the particular device configuration.  
 For further details on performance testing, see XCTestCase.h in XCTest.framework.

## Writing Swift tests

Swift controllers and models cannot access declarations internal to the app or framework from tests. In Xcode6, testing Swift internal functionality requires going through public entry points, reducing the protection provided by Swift's access controls.  
 Xcode7 provides a solution:  
 For access to Swift internals, testing tells the compiler to generate the necessary access. A new compiler control, -enable, changes this behavior, and Xcode generates accordingly when requested. The behavior is configurable and enabled by default for new projects. It does not require source changes.

Change the visibility of test entry points by modifying the import declaration. Use the new @testable import attribute in your tests without modifying the application code.

```
import Cocoa
@NSApplicationMain
class AppDelegate: NSObject, NSApplicationDelegate {
    @IBOutlet weak var window:NSWindow!
    func foo() {
        println("Hello,World!")
    }
}
```

To write a test class that can access Appdelegate, change the import in your test code to use @testable.

```
// Importing XCTestbecause of XCTestCase
import XCTest// Importing AppKitbecause of NSApplication
import AppKit

// Importing MySwiftAppbecause of AppDelegate
@testable importMySwiftApp
class MySwiftAppTests:XCTestCase {
     func testExample() {

         let appDelegate =NSApplication.sharedApplication().delegate as! AppDelegate
        *

         appDelegate.foo()

    } 
}
```

With this solution, your tests can fully access internal Swift code.

## XCTest assertions

Test methods use XCTest assertions to report results to Xcode. All assertions have a similar form: a comparison or logical expression, a failure-result format string, and arguments inserted into that string.  
 Note: The final parameter of every assertion is format…, a format string and a variable argument list. XCTest provides default failure-result strings for all assertions, and arguments may be passed into them. A Format string optionally adds a custom description of the failure, allowing a more specific explanation. This parameter is optional and can be omitted entirely.  
 For example:

```
XCTAssertEqualObjects([calcViewController.displayField stringValue], @"8", @"Part 1 failed.");
```

The assertion says: “Indicate a failure when a string created from the value of the controller’s display field is not the same as the reference string ‘8’”. If it fails, Xcode marks the failure in the test navigator and shows its description in the issues navigator, source editor, and elsewhere. A typical assertion result in the source editor looks like this:

![1](<https://allluckly.cn/images/blog/tuogao/tougao38/18.png>)

A test method may contain several assertions. If any assertion reports a failure, Xcode marks the test as failed.  
 Assertions fall into five categories: unconditional failure, equality, nil, Boolean, and exceptions.

## Assertions by category

The following sections list XCTest assertions. See XCTestAssertions.h for more information.

### Unconditional failure

XCTFail produces an unconditional failure.

```
XCTFail(format...)
```

### Equality tests

XCTAssertEqualObjectes: Reports failure when expresson1 is not equal to expresson2, or when one object is nil and the other is not.

```
XCTAssertEqualObjects(expression1, expression2, format...)
```

XCTAssertNotEqualObjects: Reports failure when expression1 equals expression2.

```
XCTAssertNotEqualObjects(expression1, expression2, format...)
```

XCTAssertEqual: Reports failure when expression1 is not equal to expression2. This assertion is for C scalar values.

```
XCTAssertEqual(expression1, expression2, format...)
```

XCTAssertNotEqual: Reports failure when expression1 equals expression2. This assertion is for C scalar values.

```
XCTAssertNotEqual(expression1, expression2, format...)
```

XCTAssertEqualWithAccuracy: Reports failure when the difference between expression1 and expression2 exceeds accuracy. This is useful for scalars such as floats and doubles, where small differences prevent exact equality, but works for all scalar values.

```
XCTAssertEqualWithAccuracy(expression1, expression2, accuracy, format...)
```

XCTAssertNotEqualWithAccuracy: Reports failure when the difference between expression1 and expression2 is less than accuracy. This is useful for scalars such as floats and doubles, where small differences prevent exact equality, but works for all scalar values.

```
XCTAssertNotEqualWithAccuracy(expression1, expression2, accuracy, format...)
```

### Nil tests

XCTAssertNil: Reports failure when the expression argument is not nil.

```
XCTAssertNil(expression, format...)
```

XCTAssertNotNil: Reports failure when the expression argument is nil.

```
XCTAssertNotNil(expression, format...) <br>
```

### Boolean tests

XCTAssertTrue: Reports failure when expression evaluates to false.

```
XCTAssertTrue(expression, format...)
```

XCTAssert: Reports failure when expression evaluates to false. It is synonymous with XCTAssertTrue.

```
XCTAssert(expression, format...)
```

XCTAssertFalse: Reports failure when expression evaluates to true.

```
XCTAssertFalse(expression, format...)
```

### Exception tests

XCTAssertThrows: Reports failure when expression does not throw an exception.

```
XCTAssertThrows(expression, format...)
```

XCTAssertThrowsSpecific: Reports failure when expression does not throw an exception of the specified class.

```
XCTAssertThrowsSpecific(expression, exception_class, format...)
```

XCTAssertThrowsSpecificNamed: Reports failure when expression does not throw an exception of the specified class and name. This is useful for AppKit or Foundation APIs that throw an NSException with a specific name, such as NSInvalidArgumentException.

```
XCTAssertThrowsSpecificNamed(expression, exception_class, exception_name, format...)
```

XCTAssertNoThrow: Reports failure when expression throws an exception.

```
XCTAssertNoThrow(expression, format...)
```

XCTAssertNoThrowSpecific: Reports failure when expression throws an exception of the specified class. Other exception types are acceptable and do not cause this assertion to fail.

```
XCTAssertNoThrowSpecific(expression, exception_class, format...)
```

XCTAssertNoThrowSpecificNamed: Reports failure when expression throws an exception of the specified class and name. This is useful for AppKit or Foundation APIs that throw an NSException with a particular name, such as NSInvalidArgumentException.

```
XCTAssertNoThrowSpecificNamed(expression, exception_class, exception_name, format...)
```

### Running tests and reviewing results

The Xcode test navigator makes running tests and reviewing results easy, and several other interactive approaches are available. Which tests run depends on the test targets enabled in the scheme. The navigator lets you control included and enabled targets, classes, and methods directly, without opening the scheme editor.

### Commands for running tests

The test navigator offers quick ways to run tests as part of coding. You can also run them directly from the source editor or the Product menu.

### Using the test navigator

Hovering over a bundle, class, or method name in the test navigator reveals a Run button. Depending on where you hover, it runs an individual method, all methods in a class, or all tests in a bundle.  
 Hover over a test bundle's name and click the Run button that appears on the right to run all tests in that bundle.

![1](<https://allluckly.cn/images/blog/tuogao/tougao38/19.png>)

Hover over a class name and click the Run button that appears on the right to run every test in that class.

![1](<https://allluckly.cn/images/blog/tuogao/tougao38/20.png>)

Hover over a test method's name and click the Run button on the right to run that individual test.

![1](<https://allluckly.cn/images/blog/tuogao/tougao38/21.png>)

### Using the source editor

When a test class is open in the source editor, an indicator appears in the gutter beside each test method. Hover over it to reveal a Run button. Click it to run the method; the indicator then shows success or failure. Hover over it again to rerun the test. This mechanism runs one test at a time.

![1](<https://allluckly.cn/images/blog/tuogao/tougao38/22.png>)

Note: The indicator beside @implementation also applies to the class, letting you run all its tests.

### Using the Product menu

The Product menu includes keyboard shortcuts for running tests directly.  
 Product \> Test runs the currently active scheme. Its keyboard shortcut is Conmmand-U.  
 Product \> Build for \> Testing and Product \> Perform Action \> Test without Building separate building tests from running them. These shortcuts simplify the build-and-test process. They are particularly useful when checking warnings or errors after changing code, or when you know the current build is up to date and want to speed up testing. The keyboard shortcuts are Shift-Command-U and Control-Command-U, respectively.  
 Product \> Perform Action \> Test: While editing a test method, this dynamic command shows the method containing the cursor and lets you run it with a keyboard shortcut. Its name reflects the test to run, such as Product \> Perform Action \> Test testAddition. The shortcut is Control-Opention-Command-U. Note: The command also works from selections in a navigator. When a navigator is active, the source editor loses focus and the command takes the navigator's current selection as input. In the test navigator, select a bundle, class, or method; in the project navigator, select a test implementation file such as CalcTests.m. Product \> Perform Action \> Test Again: When a test exposes a problem during debugging or editing, returning to the last test is useful. As with Test, the command includes the test name, for example Product \> Perform Action \> Test Again testAddition. Its keyboard shortcut is Control-Option-Command-G.

### Building tests: testing applications and libraries

Application tests run in the app's context and can combine behavior across classes, libraries or frameworks, and app features. Library tests run independently of the app, exercising classes and methods in a library or framework to verify that they meet its defined requirements.  
 The two types of test bundle require different build settings. Creating a test target with the target parameter in the New Target assistant configures these settings. The assistant displays a Target drop-down offering the SampleCalc application and CalcLibrary library.

![1](<https://allluckly.cn/images/blog/tuogao/tougao38/32.png>)

Choose SampleCalc as the build product associated with this test target to configure it for testing an application. Tests run in the application's process. The test name derives from SampleCalc, and you can change it to suit your preference.

If you select CalcLibrary as the associated build product, the target assistant configures the build settings for testing a library. Xcode launches the test runtime, framework or library, and test code in a process managed by Xcode. The default product name comes from the library target, such as “CalcLibrary Tests.” Again, you can change it to suit your preference.

## Debugging tests

All standard Xcode debugging tools are available while running tests.

## The test debugging workflow

First determine whether a failure comes from a bug in the code under test or in the test method. Failures can reveal several kinds of problems: incorrect assumptions, unmet code requirements, or faulty test code. Debugging may therefore follow different workflows. Since test methods are usually small and direct, start by checking what the test intends to do and how it implements that check.  
 Some common issues worth noting:

Is the test logic correct? Is its implementation correct? Always check the literal values used as reference expectations for typos and mistakes.  
 What assumptions does the test make? For example, using an incorrect data type in a test method may introduce a range error in the code you are testing.  
 Are you using the correct assertion to report pass or fail? For example, the tested condition may require XCTAssertTure rather than XCTAsserFalse. Such mistakes are easy to make.

Assuming the premise of your test and the test method are correct, the error must be in the code under test. Locate and fix it.

### Test-specific debugging tools

Xcode has several tools specifically for locating and debugging code during testing.

Test-failure breakpoint In the BreakPoint Navigator, click Add—the plus button—and choose Add Test Failure Breakpoint to create this special breakpoint.

![1](<https://allluckly.cn/images/blog/tuogao/tougao38/37.png>)

This breakpoint interrupts testing when a method triggers a failed assertion. Stopping immediately at the failure helps locate the problem quickly. In testAddition, an incorrect reference string deliberately makes the comparison assertion fail. A test-failure breakpoint detects that assertion and stops execution there.

![1](<https://allluckly.cn/images/blog/tuogao/tougao38/38.png>)

Once the test is interrupted, stop its execution. Set a regular breakpoint before the assertion and run the test again. For convenience, use the Run button in the source-editor gutter. Continue debugging to fix the problem.

Running tests with project menu commands

While debugging tests, remember Project \> Perform Action \> Test Again and Project \> Perform Action \> Test. They offer convenient ways to rerun the last method after fixing a failure or run the method you are writing. See Using the Product menu for more information.  
 You can always run tests conveniently using the Run button in either the test navigator or the source-editor gutter.

Assistant editor categories

The assistant editor includes two specialized categories for working with particular tests.

![1](<https://allluckly.cn/images/blog/tuogao/tougao38/39.png>)

Test Callers category: After fixing a method that caused a test to fail, check whether other tests call it and still pass. Open the assistant editor and select the Test Classes category from its menu. The drop-down lets you navigate to tests that call the method and run them to ensure the fix has not introduced other problems.  
 Test Classes Category: Similar to Test Callers, but lists classes containing test methods related to the class being edited in the main source editor. It helps identify opportunities to add tests, such as new methods not yet covered by existing tests.

Exception breakpoints during testing

An exception breakpoint normally interrupts test execution when it catches an exception. Such breakpoints are usually disabled during test runs to avoid inappropriate stops at thrown exceptions. Enable one when investigating a particular problem that you want to stop and fix.
